# Deployment

## Normal delivery

Feature branch → PR → required checks and review → preview when configured → human merge to protected main → main checks → forward Supabase migrations → Vercel's GitHub Deployment Check releases the matching production build to its domain. Vercel can build while main CI runs; automatic production aliasing waits for `Production database ready`.

Do not suppress main deployment or add a custom manual promotion pipeline. Agents do not merge or initiate production actions without explicit authorization. The owner connects GitHub/Vercel and enables main protection with the required aggregate check and review requirements.

Local development and CI pin Node 24.19.0 in .nvmrc. package.json allows Node 24.x because [Vercel manages minor and patch updates](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions). The Vercel install command explicitly runs npm 11.11.0 before installing the lockfile; packageManager alone does not select npm without Corepack.

Normal GitHub Actions jobs use fixed self-hosted resource labels: the consolidated `required` application/database/Playwright job uses `it-inventory-heavy`; production database delivery and trusted preview-access jobs use `it-inventory-light`. The mid profile remains available for reviewed workloads. Install the reviewed runtime supporting those labels before pushing a routing change; trusted-main cutover still requires owner merge. Legacy generic labels retain an 8 GiB guest. The separate diagnostic `Local runner pilot` remains restricted to its exact reviewed SHA with `it-inventory-pilot-<headSha>`. The [local runner runbook](development/local-runner.md) defines the disposable Linux runner lifecycle and host prerequisites. Repository routing does not activate or certify an installation. Record installed bundle/activation state, exact-revision pilot and recovery proof, owner acceptance of the residual detection window, and full workload results with the PR rather than treating this runbook as current host status. Before enabling active pickup, complete the documented host security checks and independent review. After normal routing is enabled on the live host, certify the full workload with the first normal PR CI run before PR readiness. Each job must receive a fresh disposable VM; destroy it after completion or cancellation before another job is accepted. PR code and secret-bearing main jobs must never share a reused VM or Docker daemon. A runner label alone does not enforce that isolation. An offline local host leaves jobs queued; there is no GitHub-hosted fallback.

Consolidation preserves the `required` check identity, exact-SHA assertions, all application/database/browser gates, trusted-main preview execution, environment secrets and the `Production database ready` deployment gate. The former `app` and `database` jobs now run as steps in `required`, removing two VM handoffs and a duplicate dependency install. Main still requires normal review and human merge; production migration delivery remains after successful required main validation and before Vercel releases the matching production build. Production credentials remain in their separately provisioned VM. Verify configured required check contexts before adopting any future check rename. Consolidation does not activate production delivery or authorize a migration run. Node setup does not use GitHub Actions npm caching. Failure-report uploads still use GitHub artifact storage on a best-effort basis; quota or service failures emit a warning without changing failed test results.

Production migration delivery requires outbound public IPv4 connectivity to the Supabase session-pooler endpoint on TCP 5432 from the disposable guest. The pinned Supabase CLI 2.116.0 `link` default saves the pooler connection using session port 5432; transaction-pooler port 6543 is not required by this path. Its fallback direct database connection uses IPv6, which the guest network does not allow. Public TCP 5432 access preserves the separate LAN, private-address, host and IPv6 denies. These are connectivity prerequisites, not evidence that the configured production endpoint is reachable or that production migration delivery has been exercised.

## Environments

Development/CI use disposable local Supabase. Previews use the already-configured Supabase nonproduction/preview branching integration with fictional data. Production uses its own project and real inventory.

### Persistent staging

The permanent `staging` Git branch mirrors only a successfully released `main` SHA. After `Foundation CI` completes successfully for a main push, the trusted `Sync staging to released production` workflow first verifies the Supabase staging branch remains persistent and bound to Git branch `staging`, then fast-forwards Git `staging` to that exact SHA. This keeps staging application code aligned with the released production version rather than with an unverified main candidate.

Supabase staging uses isolated branch project `ileoembzjxwhxgtiypec`, mapped by `[remotes.staging]` in `supabase/config.toml`. The Supabase Git integration owns staging deployment after the Git branch advances: it applies pending repository migrations and supported branch configuration automatically. The self-hosted workflow does not run a second database deployment path. Staging carries the same repository migrations/schema/configuration contract as released production while inventory rows, movement history and Storage objects remain fictional/nonproduction. Test agents may mutate fictional staging data freely; they are never authorized to target the production project.

The same trusted self-hosted workflow performs a one-way production-to-staging application-user mirror after each successful released-main sync, once daily at 11:17 UTC, and on manual dispatch. It reads production in read-only mode and writes only to the verified staging child. Supported email/password members keep their production UUID, email, confirmation state, password hash, user/app metadata, display name, role, active state and configuration-management grant, so the same password can be used on staging without copying plaintext credentials. Staging issues its own sessions; production sessions, refresh tokens, inventory data and Storage objects are never copied. Staging-only users are left alone. Mirrored users removed from production are not deleted from staging; their staging membership is deactivated and their configuration grant is removed to preserve fictional staging history. The mirror fails closed on unsupported Auth providers, identity collisions or an unexpected staging target instead of partially taking over accounts.

Vercel's Git integration owns the application side. It should deploy the permanent `staging` Git branch with staging-only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Do not set staging to the production Supabase URL. Keep PR previews separate; they remain disposable candidate environments used before merge.

The optional trusted-branch [preview staff fixture workflow](preview-staff-access.md) provisions a marked active staff account with configuration-management permission only in verified GitHub-managed PR child branches after the matching Supabase deployment succeeds. It requires separate owner-managed `preview-access` environment secrets and does not run from PR code. The configuration grant takes effect on future reconciliation after this change reaches trusted `main`.

Record the preview branch and applied repository migration revision when certifying a schema-changing preview. Do not reuse a production database or create replacement hosted projects.

## Auth provisioning

Keep the email/password provider enabled while disabling new-user signup and anonymous sign-in. Set custom SMTP before real invitations and apply the checked-in invite/recovery templates. Invitations do not grant data access until the owner creates an active viewer/staff membership.

Configuration editing is a separate, owner-granted membership capability. An owner must first verify the intended person's Auth UUID in the correct environment and read both records in the SQL editor (replace the placeholder; do not commit a real UUID):

```sql
select id, email, email_confirmed_at from auth.users
where id = '<verified-auth-uuid>'::uuid;
select user_id, display_name, role, active, can_manage_configuration
from public.app_members
where user_id = '<verified-auth-uuid>'::uuid;
```

Confirm that exactly one intended Auth user and one **active staff** membership match. Stop on a missing, inactive, viewer, or unexpected account; resolve membership identity and role separately with the owner before granting configuration access. Never grant configuration access to every staff member, the first user, or an email domain. The marked shared preview fixture receives this capability only through the separately authorized, guarded [preview workflow](preview-staff-access.md); that exception does not authorize production grants. Only after that read-first check, the owner may grant the single capability and verify the returned row:

```sql
update public.app_members
set can_manage_configuration = true
where user_id = '<verified-auth-uuid>'::uuid
  and role = 'staff' and active = true
returning user_id, role, active, can_manage_configuration;
```

Require exactly one returned row; zero means no grant occurred and needs investigation. To revoke this capability without removing ordinary inventory access, the owner sets `can_manage_configuration=false` for the same verified UUID. Application clients have no direct membership-update grant and there is no self-grant route. A production maintainer grant is an owner action outside feature-branch validation.

## Production migrations and release

After the one-time activation below, successful main CI delivers repository-controlled forward migrations automatically. These files are the canonical schema history. Do not use Supabase dashboard schema-diff or preview-branch merge output as the production migration path, and do not commit generated branch_merge_* substitutes. Disable Supabase's native production migration integration when this workflow is activated so only one writer applies migrations. PR2 migrations are additive from the existing Foundation schema; do not recreate the private schema or rewrite applied Foundation migrations.

**Except for the explicitly accepted checkpoint 5 interruption below, production migrations applied before the new application is released must remain backward-compatible with the currently deployed application. Other breaking schema changes require an expand/migrate/contract sequence.** Applied migration files are immutable: changing SQL under an already recorded version is outside this gate's detection and requires explicit review.

Before merging dependent application code, review each migration for compatibility with the currently deployed app, destructive changes, and backup/recovery readiness. Destructive or incompatible migrations outside the accepted checkpoint 5 handoff require separate explicit review and an expand/migrate/contract plan. The workflow links the pinned production project, checks that remote migration versions are a prefix of local migrations, runs a dry run, rechecks history, applies ordinary forward migrations and verifies that all checked-in versions are recorded. Migration-version mismatch, missing credentials, disabled delivery, command failure, or incomplete verification fails the readiness check. This does not inspect schema contents or detect out-of-band dashboard edits. Never reset a hosted database, apply disposable fixtures there, or leave undocumented dashboard schema changes.

Required checks and human merge authorize normal main deployment once the Deployment Check is active. The CI job runs only on an exact main push SHA after the required aggregate succeeds; PR checks remain separate. It uses the pinned Supabase CLI and suppresses credential-bearing CLI output. Main workflow runs do not cancel a running database delivery. GitHub may replace a pending run for an older main SHA when a newer push arrives; only a successful check on the production build's exact SHA can release that build. Verify that SHA, authentication/denial behavior and app health after release. Post-merge CI reports the merge SHA independently from PR-head evidence.
