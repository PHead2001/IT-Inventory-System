## Presentation lifecycle

`SpringPresence` uses one Motion spring vocabulary: 220 ms, bounce 0.08 and a
250 ms removal deadline. Only the surface moves; trigger hitboxes stay fixed.
Full motion requires a current managed presentation grant, connected visible
original host and the existing route owner's current veto. Reduced motion,
hidden documents, absent native animation support and denied animation admission
settle immediately. No animation hook reads stored preferences before fresh
privacy admission.

Semantic close immediately makes outgoing content inert, hidden from assistive
technology and blocked at click, key and submit capture. A consumer may retain
only its original mounted subtree for the short visual exit. Withdrawal cancels
local animation and removes the private exit immediately; it never preserves an
outgoing privacy grant or changes route/auth epochs. Released frame and library
callbacks recheck current original-owner admission.

`SpringDisclosure` keeps native details/summary before hydration, adopts the
actual native open state and retains form state when collapsed. Summary remains
the sole activation control. The primitive does not decide whether a task,
navigation, draft discard or mutation may proceed.

Task switches retain keyed siblings under one stable parent, at most one outgoing
instance. Existing dirty/pending/uncertain/discard guards approve the switch
before retirement. Each original task instance fences report, discard
registration (including null cleanup), reset, warning and close callbacks. Its
outgoing eligibility and route capture are disabled; the active task's existing
instance, record-version wait and focus rules do not wait for animation. DOM
labels and ARIA associations use mounted form IDs separate from business/retry
identity.
`TaskInteractionContext` adds only a start veto for the original task instance;
it grants no authorization and never cancels a business write already accepted.

## Supplementary notices

The protected provider owns one presenter with a maximum of three generic
confirmations. A ticket
captures an existing user operation before dispatch; a current successful changed
metadata result with its committed event ID, or a committed nonempty queue
addition, confirms it. No-op, error, pending, restored and after-print paths do
not create notices. Suppressed/full/withdrawn signals cannot form a later
backlog. W07 receipts and checkmarks retain their separate deduplication owners.
Linked additions use a bounded local token captured when their existing request
starts; a large valid selection cannot exceed the ticket limit by including its
record identities.

Notices appear at the bottom on phones and bottom-right on desktop. Their
five-second lifetime counts only unpaused time; hover and focus pause it.
Messages are polite status announcements, with Dismiss and Escape available and
no automatic focus capture. Dismissal returns focus only to an eligible trigger
and verifies that native focus succeeded. A disabled or unfocusable trigger falls
back to the existing main-content target before the focused notice retires.
Inline receipts remain available after the transient
notice disappears. Linked and manual additions give successful toast publication
ownership of the success announcement while retaining visible inline feedback.
A suppressed toast leaves the inline success live; mixed linked errors/limits
retain a separate polite announcement without repeating the successful addition.
Publication is motion-independent; only animated entry/exit
uses the Full route-motion veto.

The toast DOM registers painted CSS-pixel obstruction rectangles with its actual
Document. Room canvases subscribe only while connected, combine their own local
controls with authorized global cards from that Document, and retain existing
packing budgets and selection authority. Hidden/withdrawn/disconnected cards and
foreign documents cannot obstruct a room. There is no idle layout loop.
