# Labels, scanning, and stock status

This feature adds record labels and read-only scan navigation, item-wide reorder thresholds, a low-stock overview, and caller-scoped CSV downloads. It extends the existing inventory records, location hierarchy, authentication, and RLS. Labels and scans never mutate inventory; exports do not change stored values.

## Labels and stable destinations

QR labels are the default. A location label identifies its immutable location code; an asset or quantity-definition label identifies its UUID, so ordinary display-name, stock-count, or storage-location changes do not invalidate it. Room, shelf, section, drawer, rack, and container labels can represent aggregate locations. Opening an aggregate shows inventory below it; the aggregate does not become a valid stock destination. A label is an identifier only and grants no access.

The application creates QR codes locally with `qrcode`. A location QR encodes the configured origin plus `/locations/CODE`; an asset QR encodes `/inventory/assets/UUID`; a quantity QR encodes `/inventory/quantity/UUID`. Asset, quantity, and location detail views and the label-selection screen provide print preview. QR URLs use the configured application origin (`APP_ORIGIN`, then the Vercel branch URL in previews, then localhost as documented in [deployment](deployment.md)); production labels must use the stable production origin. Preview labels are environment-specific and should not be used as production labels. The application does not infer or provision a missing production origin. Without a configured production `APP_ORIGIN`, absolute-URL scan input and label generation fail closed with a configuration message. Relative internal paths, `LOC:`/`AST:` payloads, and bare exact identifiers remain available; they do not need an absolute origin.

Optional Code 128 labels use `LOC:CODE` for a location and `AST:tag` for an existing asset tag, rendered locally with `jsbarcode`. Asset tags are never generated by this feature; use a QR label if an asset has no suitable tag. If a tag changes, its Code 128 label needs reprinting. If the tag is not printable-compatible or the encoded bar width does not fit, the label uses QR instead. The shared scan parser accepts only exact application-origin URLs on canonical location/asset/quantity paths, the prefixed payloads, or bare exact identifiers. A bare identifier that matches more than one record requires the user to choose. The `/scan` page first uses `@zxing/browser` for QR and Code 128, then tries a bounded `jsqr` QR decode on ordinary ZXing frame misses; it keeps the existing scan interval and does not run a second camera loop. A fallback result goes through the same resolver, so only documented formats and same-environment destinations open. Decoded content is untrusted: malformed, oversized, external, and cross-environment destinations are rejected. Login return paths are restricted to validated internal destinations and are checked again after authentication and membership verification. Unknown or inactive records are reported as such, not guessed from a similar name.

Scanning starts only after the user chooses to start the camera. The scan page offers rear-camera preference, explicit Start, Stop/Retry, permission and availability feedback, and manual/paste entry. Completion, closing, or navigation releases the camera. Repeated reads of a frame do not repeatedly navigate. Manual lookup, ordinary search, and direct label links remain available without camera permission; access to records continues to rely on current membership and RLS.

Printed labels are black on white with readable identifiers, useful context, and code quiet zones. The default physical label is 90 × 50 mm on US Letter with a 30 mm QR code. Controls also provide 70 × 35 mm labels with a 22 mm QR code and A4 page format. Print CSS uses an 8 mm page margin, 3 mm between labels, and a four-module QR quiet zone. Nonproduction labels show a preview marker. Browser print and Save as PDF are supported; page breaks keep labels together and long names must remain readable. Printing is not an inventory mutation. Local browser or simulated-frame checks do not establish real-phone camera performance or physical printer output; record those checks separately during acceptance.

The label screen now supports a mixed print queue of quantity definitions, serialized assets, and locations. Search returns one result per record **before** count and pagination, even if a quantity definition has several current holdings. It includes zero-stock definitions; archived quantity definitions and retired assets appear with the explicit historical filter. Search covers name, serial number, asset tag, category, manufacturer, model, and UUID. Location and category filters narrow the candidate set. Queue limits are 200 distinct records, 1–100 copies per record, and 500 physical labels. The queue, filters, and print size/page/code choices persist in browser `sessionStorage` under the member and configured environment origin and clear on sign-out. This is a local print job, not a saved label registry.

A quantity label always uses a QR URL with the configured origin plus `/inventory/quantity/UUID`; it identifies the definition, not one holding or a recorded total. Choosing Code 128 for a mixed job shows a QR fallback for quantity definitions and for assets without a suitable tag. Existing location `LOC:CODE`, asset `AST:tag`, and canonical location/asset QR payloads remain valid. All codes still open current read-only detail through membership and RLS. A printed quantity QR remains linked to the definition after stock moves or count changes.

Preparing the queue re-resolves the exact selected IDs in one caller-scoped read, refreshes ordinary names/category/location context, and builds the full preview for all copies. Missing or inaccessible records block printing. An archived, retired, or inactive record requires explicit acknowledgement even when first added. A changed asset tag or lifecycle state requires renewed acknowledgement, followed by a fresh preview. Immediately before `Print selected labels / Save as PDF`, another exact-ID read checks that the preview is still current and that every code is ready. Ordinary descriptive changes update the rendered labels and show a small notice without interrupting printing. A Code 128 job that falls back to QR requires explicit acknowledgement before printing. Use the application's Print button: direct browser Ctrl/Cmd+P does not revalidate and omits the label sheet. Labels show current data without offering per-entry text overrides.

## Reorder thresholds and low-stock reads

A quantity definition may have one nullable, nonnegative 32-bit whole-unit reorder threshold (0 through 2,147,483,647). `null` disables monitoring and is the default, including for existing records. A monitored active, nonarchived definition needs restocking when its authoritative total across all current balances is less than or equal to its threshold. Balances at inactive locations remain in the total. Threshold zero warns only at zero. Out of stock means a monitored item with total zero and is a subset of needs-restocking. The dashboard counts each definition once. Moving stock between locations does not change item-wide status. Archived definitions are excluded, and restoring one retains its threshold.

Threshold edits use the existing staff-only mutation and history approach, recording actor and before/after metadata without creating quantity deltas or movement events. Viewers may read thresholds but cannot change them. An older update caller that omits the field preserves the current value; explicit `null` clears it. Quantity detail loads authoritative `stockSummary` separately from the editable item metadata and its optimistic-version baseline, so a fresh stock summary does not silently advance the metadata version or overwrite pending threshold edits. Optimistic versions and idempotent retry behavior continue to apply.

`inventory_search_v2` accepts `p_low_stock` and supplies inventory results with `reorder_threshold`, `recorded_total`, and `stock_state` (`disabled`, `in_stock`, `needs_restocking`, `out_of_stock`, or `archived`; serialized assets have no stock state). `low_stock_dashboard(p_page, p_page_size)` supplies configured, needs-restocking, and out-of-stock counts and one row per item needing attention. Needs-restocking includes out-of-stock. Totals are computed from balances under existing authorization; the feature does not maintain a duplicate total or a separately mutable low-stock flag. A location filter selects matching inventory context and does not redefine the global threshold as a per-location threshold. The interface distinguishes no configured thresholds from configured thresholds with no items needing attention, and provides a manual refresh path.

## CSV downloads

Authenticated `GET /api/exports/inventory` downloads are private/no-store and use the current member's access scope. Use `?export=low_stock` to download one row per low-stock definition; the default export is filtered inventory. Inventory export honors existing search, category, type, status, and location/subtree filters and includes all matching rows rather than only the visible page. Quantity rows represent one location holding; an active zero-stock definition is included once as an unlocated row. Serialized assets are one row each. Low-stock export is one row per quantity definition and includes its total, threshold, state, and an `All Current Holdings and Locations` context listing every holding for each selected definition, even when a filter matched only one of its holdings. It does not repeat the item-wide total once per holding.

`inventory_export_snapshot` accepts the ordinary inventory filters plus `p_low_stock` and `p_export_type` (`inventory` or `low_stock`). It reads one consistent SQL snapshot and returns rows, total, and `exported_at`. The bounded result is capped at 10,000 rows; an over-limit request returns HTTP 413 with an explicit error and never silently truncates. Empty matches still produce a CSV header. Inventory headers are Record ID, Type, Name, Category, Manufacturer, Model, Asset Tag, Serial Number, Status, Quantity at Location, Location Name, Location Code, Location Breadcrumb, Exported At (UTC), and Environment. Low-stock headers are Record ID, Type, Name, Category, Manufacturer, Model, Status, Recorded Total, Reorder Threshold, Stock State, All Current Holdings and Locations, Exported At (UTC), and Environment. Environment is `Preview` or `Production`. Inventory rows do not repeat the item-wide total. Requests above the configured limit fail with `P1013` (`export_too_large`). Filenames are `inventory-YYYYMMDDTHHMMSSZ.csv` or `low-stock-YYYYMMDDTHHMMSSZ.csv`; nonproduction filenames add a `preview-` prefix. CSV text is UTF-8 with a BOM and conventional quoting for commas, quotes, and line breaks; user-controlled cells are protected by apostrophe neutralization against spreadsheet formula interpretation, including leading whitespace/control characters. This affects only the export representation. Import identifiers as text in spreadsheet software when leading zeros must be preserved; the CSV does not add formulas to force spreadsheet typing.

Both staff and viewers can export inventory they can already read. The feature adds no import, bulk mutation, styled report, or export-job service.
