# Labels, scanning, and stock status

This feature adds record labels and read-only scan navigation, item-wide reorder thresholds, a low-stock overview, and caller-scoped CSV downloads. It extends the existing inventory records, location hierarchy, authentication, and RLS. Labels and scans never mutate inventory; exports do not change stored values.

## Labels and stable destinations

Settings and the current print job use the same **Label size**, **Paper size**, and **Barcode type** names and physical units. The screen option **QR code** explains that scanning opens the linked inventory record or location; **Code 128 when it fits** is a preference, with the existing explicit QR fallback acknowledgement. These descriptions stay outside the printed label sheet. Stored `size`, `page`, and `format` keys and barcode payloads are unchanged.

Settings saves shared starting defaults through the existing configuration-maintainer permission and version checks. Labels changes only the current job; it does not save shared defaults. Updating defaults does not overwrite the current queue or an already-open job. New jobs retain the existing initialization and queue recovery rules.

QR labels are the default. A location label identifies its immutable location code; an asset or quantity-definition label identifies its UUID, so ordinary display-name, stock-count, or storage-location changes do not invalidate it. Room, shelf, section, drawer, rack, and container labels can represent aggregate locations. Opening an aggregate shows inventory below it; the aggregate does not become a valid stock destination. A label is an identifier only and grants no access.

The application creates QR codes locally with `qrcode`. A location QR encodes the configured origin plus `/locations/CODE`; an asset QR encodes `/inventory/assets/UUID`; a quantity QR encodes `/inventory/quantity/UUID`. Asset, quantity, and location detail views and the label-selection screen provide print preview. QR URLs use the configured application origin (`APP_ORIGIN`, then the Vercel branch URL in previews, then localhost as documented in [deployment](deployment.md)); production labels must use the stable production origin. Preview labels are environment-specific and should not be used as production labels. The application does not infer or provision a missing production origin. Without a configured production `APP_ORIGIN`, absolute-URL scan input and label generation fail closed with a configuration message. Relative internal paths, `LOC:`/`AST:` payloads, and bare exact identifiers remain available; they do not need an absolute origin.

Optional Code 128 labels use `LOC:CODE` for a location and `AST:tag` for an existing asset tag, rendered locally with `jsbarcode`. Asset tags are never generated by this feature; use a QR label if an asset has no suitable tag. If a tag changes, its Code 128 label needs reprinting. If the tag is not printable-compatible or the encoded bar width does not fit, the label uses QR instead. The shared scan parser accepts only exact application-origin URLs on canonical location/asset/quantity paths, the prefixed payloads, or bare exact identifiers. A bare identifier that matches more than one record requires the user to choose. The `/scan` page first uses `@zxing/browser` for QR and Code 128, then tries a bounded `jsqr` QR decode on ordinary ZXing frame misses; it keeps the existing scan interval and does not run a second camera loop. A fallback result goes through the same resolver, so only documented formats and same-environment destinations open. Decoded content is untrusted: malformed, oversized, external, and cross-environment destinations are rejected. Login return paths are restricted to validated internal destinations and are checked again after authentication and membership verification. Unknown or inactive records are reported as such, not guessed from a similar name.

Scanning starts only after the user chooses to start the camera. The scan page offers rear-camera preference, explicit Start, Stop/Retry, permission and availability feedback, and manual/paste entry. Completion, closing, or navigation releases the camera. Repeated reads of a frame do not repeatedly navigate. Manual lookup, ordinary search, and direct label links remain available without camera permission; access to records continues to rely on current membership and RLS.

Printed labels are black on white with readable identifiers, curated record-owned product context, and code quiet zones. Quantity labels show the name, optional Item code, category and available manufacturer/model facts. Asset labels show the name, asset tag and/or serial as appropriate, category and available manufacturer/model facts. Location labels show their own name, code and hierarchy. Current balances, holding counts, availability, stock diagnostics, current storage/site assignment and lifecycle warnings belong in the screen queue, not on permanent stickers. The resolver returns those live facts separately from typed print fields. The default physical label is 90 × 50 mm on US Letter with a 30 mm QR code. Controls also provide 70 × 35 mm labels with a 22 mm QR code and A4 page format. Print CSS uses an 8 mm page margin, 3 mm between labels, and a four-module QR quiet zone. Nonproduction labels show a preview marker. Browser print and Save as PDF are supported; page breaks keep labels together and long names must remain readable. Printing is not an inventory mutation. Local browser or simulated-frame checks do not establish real-phone camera performance or physical printer output; record those checks separately during acceptance.

The label screen now supports a mixed print queue of quantity definitions, serialized assets, and locations. Search returns one result per record **before** count and pagination, even if a quantity definition has several current holdings. It includes zero-stock definitions; archived quantity definitions and retired assets appear with the explicit historical filter. Search covers name, serial number, asset tag, category, manufacturer, model, and UUID. Location and category filters narrow the candidate set. Queue limits are 200 distinct records, 1–100 copies per record, and 500 physical labels. The queue, filters, and print size/page/code choices persist in browser `sessionStorage` under the member and configured environment origin and clear on sign-out. This is a local print job, not a saved label registry.

Asset, quantity and location add links represent one-time navigation intents. The screen restores the saved queue first, then authorizes each exact linked record, merges additions without replacing saved copies/settings, and removes only handled add parameters with a router replacement. Other query state and the hash remain intact. Failed lookups retain their intent for explicit retry. Remove cancels the matching pending addition; Clear queue cancels every pending addition. Late lookup or preview responses cannot restore removed records, and a later intentional Print label action can add the same record again. Lifecycle warnings are limited to the current queue, so removing the last affected record clears its obsolete warning immediately. If browser persistence fails, the screen warns that removals may not survive reload and previously saved records may return.

Independent authorized manual and linked additions merge the latest queue when either lookup finishes. Removing one pending linked record preserves unrelated pending additions. Clear remains available for a failed pending link even when the queue is empty, and changing member or environment cancels old lookup continuations.

Unresolved linked records appear as pending additions with individual Remove controls. Their requested IDs or location codes identify which addition is being cancelled without displaying unverified record details. Pending additions do not count as confirmed labels and never enter the print sheet; their controls remain available if lookup fails, alongside explicit retry and Clear.

Quantity Item codes (SKU) are optional human-readable identifiers on quantity definitions. Label search, ordinary inventory search, and CSV downloads include them. A quantity label prints its current Item code when set; its QR destination remains the stable quantity UUID. Codes remain reserved while a definition is archived. Bare manual identifiers check exact case-insensitive Item code matches alongside locations and asset tags and ask the user to choose when namespaces collide. The scan page also has an explicit **Quantity Item code (SKU)** manual mode for codes such as `/SKU` or `AST:001`; in this mode URL-like text is matched only as stored data. Camera scans and ordinary label mode keep the canonical same-origin URL and `LOC:`/`AST:` rules.

A quantity label always uses a QR URL with the configured origin plus `/inventory/quantity/UUID`; it identifies the definition, not one holding or a recorded total. Choosing Code 128 for a mixed job shows a QR fallback for quantity definitions and for assets without a suitable tag. Fallback explanations and required acknowledgement stay on screen, outside the printable sheet; the QR label itself is clean. Existing location `LOC:CODE`, asset `AST:tag`, and canonical location/asset QR payloads remain valid. All codes still open current read-only detail through membership and RLS. A printed quantity QR remains linked to the definition after stock moves or count changes.

A changed label item appears in one named decision panel with its tracking type and the observed state or verified transition. Review item expands the current caller-authorized snapshot; visiting its detail link does not acknowledge it. Historical records require an explicit historical-print checkbox and Acknowledge reviewed item. Acceptance rechecks the exact current queue and the reviewed identity, tag, state and printable code data before accepting that item, then refreshes the preview. Other affected items need their own decisions. Any observed identifier/lifecycle change latches an outstanding review in the saved queue, including a return to active before acknowledgment. Returning focus to Labels refreshes the queue and invalidates an open review; unavailable records lose cached names and print content and offer safe removal guidance. Removal clears only the removed item's decision and obsolete responses cannot restore it. A surviving checked review stays blocked until an exact fresh snapshot matches, then becomes actionable again; a changed or missing survivor requires a new decision. These checks compare observed snapshots; the read contract does not expose a lifecycle event version and cannot identify an unobserved transition that returns to the same snapshot.

Preparing the queue re-resolves the exact selected IDs in one caller-scoped read, refreshes on-screen holdings and record-owned print fields, and builds the full preview for all copies. Missing or inaccessible records block printing. An archived, retired, or inactive record requires explicit acknowledgement even when first added. A changed asset tag or lifecycle state requires renewed acknowledgement, followed by a fresh preview. Immediately before `Print selected labels / Save as PDF`, another exact-ID read checks that the preview is still current and that every code is ready. Printable descriptive changes update the rendered labels and show a small notice without interrupting printing; holdings-only changes update screen context without regenerating the print sheet. A Code 128 job that falls back to QR requires explicit acknowledgement before printing. Use the application's Print button: direct browser Ctrl/Cmd+P does not revalidate and omits the label sheet. Labels show current data without offering per-entry text overrides.

## Reorder thresholds and low-stock reads

The overview shows neutral “Not configured” alert summaries when no active quantity definitions have thresholds. Its nearby coverage summary identifies the monitored set and links to the permitted quantity read/detail path. Configured healthy monitoring shows real zero alerts, including threshold zero; unavailable reads never become healthy zero or unconfigured success. Shared count copy distinguishes singular/plural stock units, holdings, definitions, assets, events, records and label copies. Printed identities and custom unit labels are unchanged.

A quantity definition may have one nullable, nonnegative 32-bit whole-unit reorder threshold (0 through 2,147,483,647). `null` disables monitoring and is the default, including for existing records. A monitored active, nonarchived definition needs restocking when its authoritative **available storage** total is less than or equal to its threshold. Balances at inactive storage locations remain available until moved; units assigned to sites contribute to `Total Recorded` but are unavailable for a new issue. Threshold zero warns only at zero available units. Out of stock means a monitored item with zero available storage units and is a subset of needs-restocking. The dashboard counts each definition once. Moving stock between storage locations does not change item-wide status; issuing to or returning from a site may. Archived definitions are excluded, and restoring one retains its threshold.

Threshold edits use the existing staff-only mutation and history approach, recording actor and before/after metadata without creating quantity deltas or movement events. Viewers may read thresholds but cannot change them. An older update caller that omits the field preserves the current value; explicit `null` clears it. Quantity detail loads authoritative `stockSummary` separately from the editable item metadata and its optimistic-version baseline, so a fresh stock summary does not silently advance the metadata version or overwrite pending threshold edits. Optimistic versions and idempotent retry behavior continue to apply.

`inventory_search_v3` accepts `p_low_stock` and returns `reorder_threshold`, `stock_state`, and decimal-string available, assigned, and recorded totals (`disabled`, `in_stock`, `needs_restocking`, `out_of_stock`, or `archived`; serialized assets have no stock state). `low_stock_dashboard(p_page, p_page_size)` supplies configured, needs-restocking, and out-of-stock counts and one row per item needing attention. Needs-restocking includes out-of-stock. Dashboard status and all three totals come from one statement snapshot; the feature does not maintain a duplicate total or a separately mutable low-stock flag. A location or site filter selects matching inventory context and does not redefine the global availability threshold as a per-location or per-site threshold. The interface distinguishes no configured thresholds from configured thresholds with no items needing attention, and provides a manual refresh path.

## CSV downloads

Operational display-zone precedence and export time presentation are defined in [shared time presentation](shared-time.md). The canonical UTC column prefix remains unchanged; display timezone metadata is appended after existing columns. The display export time uses the database snapshot's generation instant and the validated `displayTimeZone` query, rather than a browser download time.

Authenticated `GET /api/exports/inventory` downloads are private/no-store and use the current member's access scope. Use `?export=low_stock` to download one row per low-stock definition; the default export is filtered inventory. Inventory export honors search, category, type, status, location/subtree, and site filters and includes all matching rows rather than only the visible page. Quantity rows represent one current storage or site holding; an active zero-stock definition is included once as an unlocated row. Serialized assets are one row each. Physical `Quantity at Location` remains on every holding row. The item-wide `Available in Storage`, `Assigned to Sites`, and `Total Recorded` values appear only on the first row for each quantity definition in the final deterministic filtered export order; later rows for that definition have blank total cells. A site- or location-filtered export still shows those totals once for each selected definition. Ordinary holding rows omit the legacy `recorded_total` field entirely. Low-stock export is one row per quantity definition and includes its item-wide total, threshold, state, and an `All Current Holdings and Locations` context listing every holding for each selected definition, even when a filter matched only one of its holdings.

`inventory_export_snapshot_v3` accepts the ordinary inventory filters, optional site ID, `p_low_stock`, and `p_export_type` (`inventory` or `low_stock`). It reads one consistent SQL snapshot and returns rows, total, and `exported_at`. The bounded result is capped at 10,000 rows; an over-limit request returns HTTP 413 with an explicit error and never silently truncates. Empty matches still produce a CSV header. Inventory headers include holding location/site identity and custody type, followed by `Available in Storage (Item-wide)`, `Assigned to Sites (Item-wide)`, and `Total Recorded (Item-wide)`. Low-stock headers include `Total Recorded`, `Available in Storage`, `Assigned to Sites`, threshold, state, and all-current-holdings context. Both include the export timestamp and `Preview` or `Production` environment; custom fields are an explicit opt-in column. Requests above the configured row limit fail with `P1013`. Filenames are `inventory-YYYYMMDDTHHMMSSZ.csv` or `low-stock-YYYYMMDDTHHMMSSZ.csv`; nonproduction filenames add a `preview-` prefix. CSV text is UTF-8 with a BOM and conventional quoting for commas, quotes, and line breaks; user-controlled cells are protected by apostrophe neutralization against spreadsheet formula interpretation, including leading whitespace/control characters. This affects only the export representation. Import identifiers as text in spreadsheet software when leading zeros must be preserved; the CSV does not add formulas to force spreadsheet typing.

Both CSV types append `Item Code (SKU)` after their existing columns, preserving established column positions. The existing raw snapshot and encoded CSV byte caps still apply.

Both staff and viewers can export inventory they can already read. The feature adds no import, bulk mutation, styled report, or export-job service.
