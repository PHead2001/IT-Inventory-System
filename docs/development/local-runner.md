# Local GitHub Actions runner (staged)

This is a **staged, inactive** replacement for paid GitHub-hosted runner capacity. The existing workflows still use `ubuntu-latest`; installing these scripts does not move a job. The host has not yet passed a Hyper-V pilot. Do not describe a local runner job as certified until a real one-job pilot, cleanup verification, and independent security review have completed.

The design runs one repository-scoped, just-in-time GitHub runner in one fresh Ubuntu 24.04 Hyper-V VM at a time. A persistent Windows SYSTEM supervisor looks for queued jobs carrying the custom `it-inventory-ephemeral` label, creates a full copy of the clean boot disk for one job, and deletes the VM and per-job files when the runner exits. A separate SYSTEM watchdog runs every minute and at boot; it removes the recorded VM when its hard deadline expires, its supervisor dies, or Windows restarts. Restart always destroys the old VM before a new one can be launched. No host directory or cross-job package cache is mounted in the VM. The guest receives only its per-VM SSH public key and a one-job JIT configuration; the repository PAT stays on Windows.

## Owner setup

Double-click `scripts/local-runner/Setup.cmd` and accept the Windows elevation prompt. Its small menu offers **Enable Hyper-V**, **Install or resume**, and **Store GitHub token**. Enabling the feature never restarts Windows automatically; restart if Windows requests it, then open Setup again and choose Install. A failed step stays visible and can be retried from the menu. The defaults target `PHead2001/IT-Inventory-System` and GitHub's default runner group ID `1`; the JIT API will reject an invalid group rather than silently choose another repository. Setup stops if another Windows NAT occupies the host, including one used by Rancher/WSL. It never removes or changes that NAT, the Rancher distribution, or an existing VM.

Setup downloads two fixed official Ubuntu artifacts with pinned SHA-256 values: the generic [Noble cloud QCOW2 image](https://cloud-images.ubuntu.com/releases/noble/release-20260926/) and [Ubuntu 24.04.5 WSL image](https://releases.ubuntu.com/24.04/). A dedicated WSL image converter only installs `qemu-utils` and converts the verified QCOW2 into a Hyper-V VHDX. Its random distribution name is recorded in the protected setup stage before import; resume requires the same Windows WSL registration and owned base path. An unrecognized or preexisting converter is refused. It sees no repository code, job data, or GitHub credential. Conversion writes a temporary VHDX, validates and resizes it, then records the completed output hash. Resume verifies both the source and output hashes; a partial or unreceipted VHDX is regenerated. The Azure VHD is intentionally excluded: [Canonical says it will not work on local Hyper-V](https://ubuntu.com/docs/public-images/public-images-reference/artifacts/). Canonical documents [generic image conversion and NoCloud on Hyper-V](https://ubuntu.com/blog/how-to-use-ubuntu-on-windows). The full converted VHDX is copied for each job, never attached as a shared parent disk.

Setup creates `C:\ProgramData\ITInventoryLocalRunner`, its dedicated image-converter WSL distribution, a dedicated internal switch/NAT on `172.30.240.0/29`, and three SYSTEM tasks. It protects the fixed data root with a non-inheriting SYSTEM/Administrators-only ACL and refuses an unexpected owner, reparse point, conflicting switch/NAT, or overlapping host address. Partial setup can be rerun for the same repository/group using its tagged setup stage; it never adopts a reserved switch/NAT that existed before its own stage. It leaves job pickup disabled.

Create a **fine-grained GitHub PAT limited to this one repository**, with repository **Administration: read/write** for JIT runner registration and **Actions: read** for queued-job inspection. Choose **Store GitHub token** in the Setup menu and paste the token only into that local secure prompt. The credential is encrypted with Windows DPAPI LocalMachine, stored under the SYSTEM/Administrators-only root, and never written to the guest or workflow. Local administrators are part of the trusted host boundary. Do not paste the token into chat, command arguments, `.env`, the repository, or a screenshot.

After the code and host network policy are independently reviewed, the pilot operator enables a single harmless workflow job with the custom runner label and activates the one-job pilot. The supervisor records the pilot as consumed before starting the VM, so a crash or restart cannot take a second pilot job. It accepts success only after GitHub reports the selected job completed on the exact JIT runner name and ID; another runner's success or a still-running job cannot enable active pickup. A failed or uncertain pilot remains consumed and requires maintainer investigation. `Runner.ps1 -Action EnableActive` accepts only that recorded successful pilot. Existing production environment branch restrictions remain main-only, and no workflow routing or environment settings are changed by these scripts. Changing `runs-on` is a separate reviewed step after the pilot.

Setup adds a **IT Inventory Runner** folder on the Windows Desktop with **Start**, **Restart**, **Stop**, and **Status** shortcuts. They show an elevation prompt and open a visible control window. The underlying `.cmd` controls also live in `C:\ProgramData\ITInventoryLocalRunner\bin`. Start keeps the SYSTEM supervisor running across sign-out and Windows restart; Status reports activation and the one recorded VM. Stop halts the supervisor and removes its VM. Restart stops and deletes the current VM before starting the supervisor again.

## Boundaries and pending proof

The host-side Hyper-V extended port ACL denies IPv6, private/link-local/CGNAT destinations, current host addresses and connected LAN routes, and all unlisted traffic. It allows public HTTP/HTTPS and public DNS, plus host-to-guest SSH for setup. Rules are installed and read back before VM boot and checked again before JIT registration. A live guest-to-host TCP denial and public GitHub TLS/DNS probe must pass before registration. These controls are host-side; a guest firewall rule cannot replace them. [Microsoft documents rule weights and stateful return traffic](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/create-security-policies-extended-port-access-control-lists). The pilot must validate that this exact policy works on this Windows 11 host and that Docker, Supabase, Playwright, GitHub job assignment, one-job exit, and boot/deadline cleanup work as intended. Host routing can change after registration; the pilot/review must assess that residual window before activation.

As of 2026-09-29 the current shell is not elevated and the Hyper-V PowerShell module is absent. No Windows feature, VM, WSL helper, NAT, scheduled task, PAT, JIT runner, or workflow has been created by this implementation pass. The scripts passed only non-mutating syntax and contract checks. They are not a claim that the PC can currently run CI. The next concrete host step is **Enable Hyper-V** in the Setup menu, followed by restart if required and a real isolated pilot. Existing GitHub-hosted jobs remain the current path until routing is separately changed.
