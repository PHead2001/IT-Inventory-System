# Local GitHub Actions runner (staged)

This is a **staged, inactive** replacement for paid GitHub-hosted runner capacity. The existing workflows still use `ubuntu-latest`; installing these scripts does not move a job. The host has not yet passed a Hyper-V pilot. Do not describe a local runner job as certified until a real one-job pilot, cleanup verification, and independent security review have completed.

The design runs one repository-scoped, just-in-time GitHub runner in one fresh Ubuntu 24.04 Hyper-V VM at a time. A persistent Windows SYSTEM supervisor looks for queued jobs carrying the custom `it-inventory-ephemeral` label, creates a full copy of the clean boot disk for one job, and deletes the VM and per-job files when the runner exits. The single boot-triggered supervisor first recovers the recorded old session under a lock, then begins pickup; recovery failure prevents pickup. A separate SYSTEM watchdog runs every minute and removes the recorded VM when its hard deadline expires or its supervisor/ready network guardian dies. Each VM explicitly disables automatic start and uses TurnOff at host shutdown; both settings are read back before boot. Restart always destroys the old VM before a new one can be launched. No host directory or cross-job package cache is mounted in the VM. The guest receives only its per-VM SSH public key and a one-job JIT configuration; the repository PAT stays on Windows.

## Owner setup

Double-click `scripts/local-runner/Setup.cmd` and accept the Windows elevation prompt. Its small menu offers **Enable Hyper-V**, **Install or resume**, and **Store GitHub token**. Enabling the feature never restarts Windows automatically; restart if Windows requests it, then open Setup again and choose Install. A failed step stays visible and can be retried from the menu. The defaults target `PHead2001/IT-Inventory-System` and GitHub's default runner group ID `1`; the JIT API will reject an invalid group rather than silently choose another repository. Setup stops if another Windows NAT occupies the host, including one used by Rancher/WSL. It never removes or changes that NAT, the Rancher distribution, or an existing VM.

Setup downloads two fixed official Ubuntu artifacts with pinned SHA-256 values: the generic [Noble cloud QCOW2 image](https://cloud-images.ubuntu.com/releases/noble/release-20260926/) and [Ubuntu 24.04.5 WSL image](https://releases.ubuntu.com/24.04/). A dedicated WSL image converter installs `qemu-utils` and converts the verified QCOW2 into a Hyper-V VHDX. WSL retains Windows host integration and is a trusted setup tool, not an isolated job sandbox. Its random distribution name is recorded in the protected setup stage before import; resume requires the same Windows WSL registration and owned base path. An unrecognized or preexisting converter is refused. Conversion writes a temporary VHDX, validates and resizes it, then records the completed output hash. Resume verifies both the source and output hashes; a partial or unreceipted VHDX is regenerated. Before setup completes or the token menu can run, setup verifies the exact owned converter registration, terminates it, verifies ownership again, unregisters it, and verifies its absence. Retirement failure keeps setup incomplete; retry uses the protected stage. The Azure VHD is intentionally excluded: [Canonical says it will not work on local Hyper-V](https://ubuntu.com/docs/public-images/public-images-reference/artifacts/). Canonical documents [generic image conversion and NoCloud on Hyper-V](https://ubuntu.com/blog/how-to-use-ubuntu-on-windows). The full converted VHDX is copied for each job, never attached as a shared parent disk.

Setup creates `C:\ProgramData\ITInventoryLocalRunner`, a temporary image-converter WSL distribution, a dedicated internal switch/NAT on `172.30.240.0/29`, and two SYSTEM tasks. It protects the fixed data root with a non-inheriting SYSTEM/Administrators-only ACL and refuses an unexpected owner, reparse point, conflicting switch/NAT, or overlapping host address. Partial setup can be rerun for the same repository/group using its tagged setup stage; it never adopts a reserved switch/NAT that existed before its own stage. It leaves job pickup disabled. VM creation journals a provisional identity before New-VM; recovery accepts an untagged VM only while Off, with the exact recorded GUID name, exact instance-root configuration path, and exactly the recorded boot disk. Tag readback advances that journal before any additional attachment or boot.

WSL may record the converter's registry BasePath as `\\?\C:\ProgramData\ITInventoryLocalRunner\image-converter`. Setup compares that extended DOS spelling with the same ordinary local path after narrow normalization, while still requiring the exact recorded distribution name, owned root and absence of reparse points. UNC/device paths, ambiguous extended components and genuinely different paths remain rejected. If import completed before an ownership error, retry **Install or resume** with the corrected scripts; retain the protected setup stage and registered converter rather than deleting or adopting another distribution.

Create a **fine-grained GitHub PAT limited to this one repository**, with repository **Administration: read/write** for JIT runner registration and **Actions: read** for queued-job inspection. Choose **Store GitHub token** in the Setup menu and paste the token only into that local secure prompt. The credential is encrypted with Windows DPAPI LocalMachine, stored under the SYSTEM/Administrators-only root, and never written to the guest or workflow. Local administrators are part of the trusted host boundary. Do not paste the token into chat, command arguments, `.env`, the repository, or a screenshot.

After the code and host network policy are independently reviewed, the pilot operator enables a single harmless workflow job with the custom runner label and chooses **Enable one-job pilot and start** in Setup. The supervisor records the pilot as consumed before starting the VM, so a crash or restart cannot take a second pilot job. It accepts success only after GitHub reports the selected job completed on the exact JIT runner name and ID; another runner's success or a still-running job cannot enable active pickup. A failed or uncertain pilot remains consumed and requires maintainer investigation. Setup's **Status** option reports the activation state, consumed job, recorded proof, and fixed failure stage/code; exception messages and credentials are omitted. **Enable active pickup and start** requires the successful recorded pilot. Before using that option, the owner must additionally accept live guest isolation, synthetic network-drift termination, cleanup, and the residual detection window described below. Existing production environment branch restrictions remain main-only, and no workflow routing or environment settings are changed by these scripts.

Setup adds a **IT Inventory Runner** folder on the Windows Desktop with **Start**, **Restart**, **Stop**, and **Status** shortcuts. They show an elevation prompt and open a visible control window. The underlying `.cmd` controls also live in `C:\ProgramData\ITInventoryLocalRunner\bin`. Start keeps the SYSTEM supervisor running across sign-out and Windows restart; Status reports activation and the one recorded VM. Stop halts the supervisor and removes its VM. Restart stops and deletes the current VM before starting the supervisor again.

## Boundaries and pending proof

The host-side Hyper-V extended port ACL denies IPv6, private/link-local/CGNAT destinations, current host addresses and connected LAN routes, and all unlisted traffic. It allows public HTTP/HTTPS, public TCP 5432 for the linked Supabase session endpoint, and public DNS, plus host-to-guest SSH for setup. The pinned Supabase CLI uses pooler session port 5432; port 6543 is not opened. A linked database workflow requires a public IPv4 session endpoint; these checks do not connect to production or prove actual production connectivity. Higher-priority private/host/route denies also apply to port 5432. Rules are installed and read back before VM boot and checked again before JIT registration. A live guest-to-host TCP denial and public GitHub TLS/DNS probe must pass before registration. These controls are host-side; a guest firewall rule cannot replace them. [Microsoft documents rule weights and stateful return traffic](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/create-security-policies-extended-port-access-control-lists).

A separate per-session Windows guardian starts and confirms readiness before VM boot. It compares a canonical snapshot of all host IPv4/IPv6 addresses and routes, including destination, next hop, and interface, once per second throughout cloud-init, downloads, SSH, and job execution. Address/route drift or inspection failure removes the session VM instead of adopting a new baseline; a fresh comparison also runs immediately before JIT registration. Boot holds the state lock and rechecks the session/guardian so cancelled sessions cannot subsequently start. The one-second interval plus host inspection, lock acquisition and VM stop time creates a nonzero exposure window; this is not instantaneous network isolation. The pilot must validate this exact ACL and guardian on the Windows host, including a synthetic route/address change, and exercise Docker, Supabase, Playwright, GitHub assignment, one-job exit, provisional creation recovery, and boot/deadline cleanup. Active pickup needs the owner's explicit acceptance of that measured residual window.

The repair pass performs no host provisioning, elevation, credential creation, VM/WSL/NAT/task creation, or GitHub registration. Windows PowerShell 5.1 syntax and non-mutating contract checks cover native argument fidelity, lifecycle readback, provisional cleanup, serialized recovery, synthetic network drift and inspection failure, cancelled boot, converter retirement, and menu activation order. These checks do not establish real Hyper-V networking, disk creation, guest boot, shutdown recovery or a working runner job. Complete independent review, then use Setup and a real harmless isolated pilot; package activation remains disabled until the operator explicitly enables it.
