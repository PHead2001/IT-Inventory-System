## Measurement method

Each warm scenario used five production-build browser interactions from a prepared signed-in page. The time begins just before the actual click and ends when the destination heading or selected-location content is visible; room selection additionally waits for the location panel to clear `aria-busy`. The warm route runs prime the client bundle/cache once. Fresh browser-context figures are one first load with an empty browser cache and shared signed-in cookies, while the local Next server and database remain warm. They are **not** service-cold observations. `p95` uses nearest rank, so with five samples it equals the slowest sample. The raw per-run values are in `measurements.json`.

The browser request column counts same-origin requests initiated inside the timed window, including Next prefetch and static chunks. It is not a count of database calls. The server column counts local Supabase fetches from the diagnostic. Its duration sum includes parallel requests and must not be read as elapsed critical-path time or pure PostgreSQL execution time. Browser decoded response bytes in the raw file are incomplete for some requests still streaming at collection; no transfer-size conclusion is drawn from that field. `actionResolvedMs` in the raw file is Playwright's click/URL completion, not independently observed visual feedback; content-ready time is the comparable user timing here.

The elevated browser counts on Settings management links include Next prefetches during the action window; the destination itself used three server fetches. First loads in fresh browser contexts were inventory 389 ms/22 browser requests, Settings 243 ms/20, room 160 ms/21, and detail 276 ms/21 (one sample each; no p95). Warm inventory produced eight server fetches: one Auth identity, one membership, categories, sites, locations, inventory search, metadata batch description, and thumbnail list. A room visit used identity, membership, and locations; an empty selection added inventory search, and a populated selection also added metadata description. The room transition waits for these reads before selected content appears.

The strongest measured hotspot is all-category form loading. Combined Settings made 49 `metadata_form_get` RPCs per visit, 53 Supabase fetches total. Quantity detail made the same 49 form RPCs and 61 fetches total. Across five Settings visits those form RPCs consumed 7,871 ms of summed HTTP fetch duration; across five detail visits, 7,533 ms. They overlap in time. The source at the captured SHA calls `getPublishedForms` for every category on `/settings` and in detail metadata loading. `requireMember` verifies Auth identity and membership, while nested read helpers independently invoke it; this is visible in the code, although the local fetch diagnostic observed one identity/membership pair in the warm sampled route windows. Browser network counts alone cannot establish authorization or DB cost.

The Long Tasks observer saw one >50 ms task on each base-room navigation (median 56 ms, p95 71 ms) with SwiftShader. Other sampled warm scenarios had median zero; empty/populated room selections each had one long task in the slowest of five samples (63/66 ms). This is a software-rendered desktop browser observation, not a phone GPU result.

## Before-state behavior and visual evidence

- The desktop Overview is a conventional flat column of low-stock cards, and the 390px capture retains the same dense information. The current local fixture contains several test-generated names and long identifiers; the before screenshots preserve that real local state rather than replacing it with attractive sample copy.
- The combined Settings screen is approximately 8,150 px tall at 1440px width in this fixture. Categories, label defaults, and the complete form designer appear in one document. It serializes all 49 forms even when visiting unrelated Settings work, and the dense category list pushes the designer far below the first viewport.
- The designer's actual drag handle was held over an adjacent control. `before-drag-held.png` and the video show no lifted overlay; the source control's document position did not change before release. The runtime probe reported zero drag overlays. The baseline implementation commits the move from the pointer-up handler. Continuous resize, cross-section reflow, and keyboard gesture equivalence were not exercised in this baseline probe.
- The same-user focus/visibility probe created an unsaved local field label, delayed the two verification requests, then dispatched both events. It observed **two** Settings verification POSTs. The visible “Checking configuration access…” state replaced the whole editor while pending, as `before-focus-checking.png` shows. The unsaved value survived after verification. This does not test actual idle timeout, logout, revocation, or cross-account recovery.
- The room uses its current closet scene and location picker. The populated and empty captures show actual fixture-backed selection. Software-rendered screenshots and video do not establish physical phone performance, camera behavior, or printer output.

## Comparison and omitted evidence

For a meaningful after-state comparison, repeat the same normal-motion production build, fixture density, widths, interaction starts/ready markers, five warm runs, first-cache context, and local fetch diagnostic. Keep a separate record for deliberate changes in fixture count, server warmth, browser version, and hardware. Do not compare a motion-disabled after build with this normal baseline. The current capture has no direct SQL execution timing, server-render phase breakdown, deterministic first visual-feedback marker for every route, real idle/revocation reproduction, physical-device GPU timing, or hosted network/SLA data. Those remain distinct acceptance checks; the browser and Supabase HTTP timings here must not be relabeled as them.
