# Staff fixture for GitHub-managed previews

After this workflow is merged into the trusted default branch, `.github/workflows/preview-access.yml` reconciles an isolated Supabase preview for each open, same-repository PR, including stacked PRs targeting another branch in this repository. It runs on PR changes targeting `main`, a manual PR-number dispatch, and every 30 minutes; the schedule also picks up stacked PRs targeting another same-repository branch. A secret-free discovery job lists eligible open PRs. GitHub then runs a separate trusted provisioning job per PR, with at most four jobs in parallel and a five-minute timeout for each. A slow preview cannot consume another PR's timeout. It does not wait for Foundation CI to pass. It does wait for the Supabase Preview check produced for the current PR head commit, branch health, and the required membership schema. A new or reset branch can therefore become usable without a passing application test.

The account is `test@gmail.com`, email-confirmed, with a six-digit password held only in the `preview-access` GitHub environment. It has an active `staff` row with `can_manage_configuration=false`. The Auth user carries `app_metadata.inventory_preview_fixture=true`, which is controlled by the administrator. An existing account at that email without this marker stops reconciliation; the workflow never takes it over. Repeated runs reset the marked user's password, clear its Auth ban, and restore its staff membership. The account and data exist only in a verified nondefault child of parent project `dndqydmuqoduwaoujfki`; closing/deleting a preview follows Supabase's ordinary branch lifecycle.

## Activation

An owner must create a dedicated GitHub environment named `preview-access`, restrict its deployment branch policy to `main` only, and verify that restriction before adding any secrets. The environment name alone does not enforce this. The workflow also skips its privileged job unless `github.ref` is `refs/heads/main`. Do not copy any `production-database` environment secrets.

- Environment secret `PREVIEW_SUPABASE_MANAGEMENT_TOKEN`: a Supabase Management API token with only the access needed to read the parent's branch list, read/update the verified child Auth configuration, and reveal that child's API keys. This is not the production database password or an application service key.
- Environment secret `PREVIEW_STAFF_PASSWORD`: the requested six-digit test password. The value is never printed, stored in this repository, or put in an artifact.
- Environment variable `PREVIEW_ALLOW_SIX_DIGIT_MINIMUM`: set to `true` only after explicit owner approval of reducing a verified preview child's Auth minimum password length to six. Without that approval, the job stops before writes when the inherited minimum exceeds six. It never changes required-character or breached-password settings; an incompatible setting requires manual review. Signup must already be disabled.

The owner must confirm that the Supabase GitHub integration is connected to this repository and its `Supabase Preview` check is emitted by the Supabase GitHub App for each PR head revision. The Management API response must expose the branch's exact `git_branch`, `pr_number`, parent ref, nondefault flag, health, and latest check-run ID. The child project must have a default `secret` and `publishable` API key. The deployed migrations must expose `app_members(user_id,role,active,can_manage_configuration)` through the Data API with the expected membership permissions. Missing prerequisites cause a bounded failure and can be reconciled by the next run or manual dispatch.

Both discovery and provisioning check out `main` by name, never PR code, and run only Node built-ins. The discovery job has no privileged environment or Supabase secrets. Its GitHub token has repository read, PR read, and checks read. It fetches the open PR and Supabase branch afresh, matches both exact branch name and PR number, verifies parent and nondefault child, and checks the Supabase App check's successful conclusion at the current PR SHA before changing Auth policy, user, or membership. It repeats these identity checks immediately before each mutation. Forked, closed, retargeted, stale, ambiguous, wrong-parent, and default targets are refused. No production project URL or key is constructed for the provisioning calls.

The script uses the verified child's temporary admin key only inside the workflow process to create or update the Auth user and `app_members` row, then signs in with the real password and reads the membership as that user. It does not call signup, invite, email, inventory, or production endpoints. Workflow logs contain PR number, abbreviated public commit SHA, and generic status only; HTTP error bodies are intentionally suppressed.

## Local validation

Run `npm run test:preview-access` and `node --check scripts/preview-access.mjs`. The preview test is included in `npm run validate:app`. The tests use fake API adapters and make no hosted writes. They cover idempotent reconciliation, password reset, sign-in/membership verification, and zero-write refusals for fork, stale revision, default/parent/wrong-parent branch, invalid check identity, and absent schema. A real hosted branch/account verification remains necessary after environment activation and trusted-branch merge.

The flow is intentionally limited to GitHub-managed PR previews. It does not provision arbitrary manual Supabase branches.
