# Staff and file keys for GitHub-managed previews

After this workflow is merged into the trusted default branch, `.github/workflows/preview-access.yml` reconciles an isolated Supabase preview for each open, same-repository PR, including stacked PRs targeting another branch in this repository. It runs on PR changes targeting `main` and on manual PR-number dispatch. There is no recurring schedule, so an idle repository consumes no periodic runner quota. Stacked PRs targeting another same-repository branch can be reconciled manually by PR number. A secret-free discovery job validates the requested PR. GitHub then runs a separate trusted provisioning job per PR, with at most four jobs in parallel and a fifteen-minute timeout for each. A slow preview cannot consume another PR's timeout. It does not wait for Foundation CI to pass. It does wait for the Supabase Preview check produced for the current PR head commit, branch health, and the required membership schema. A new or reset branch can therefore become usable without a passing application test.

## Activation

An owner must create a dedicated GitHub environment named `preview-access`, restrict its deployment branch policy to `main` only, and verify that restriction before adding any secrets. The environment name alone does not enforce this. The workflow also skips its privileged job unless `github.ref` is `refs/heads/main`. Do not copy any `production-database` environment secrets.

- Environment secret `PREVIEW_SUPABASE_MANAGEMENT_TOKEN`: a dedicated Supabase Management API token scoped in the provider UI to the parent IT project, with Development Branches Read, API Keys Read, API Key Secrets Read, Auth Config Read/Write, and Project Settings Read/Write. Provider project scope may still authorize production resources on that parent; the workflow's branch and project-reference guards enforce preview-only writes. This is not the production database password or an application service key. Verify that the token can read future GitHub-created child branches after activation.
- Environment secret `PREVIEW_STAFF_PASSWORD`: the requested six-digit test password. The value is never printed, stored in this repository, or put in an artifact.
- Environment variable `PREVIEW_ALLOW_SIX_DIGIT_MINIMUM`: set to `true` only after explicit owner approval of reducing a verified preview child's Auth minimum password length to six. Without that approval, the job stops before writes when the inherited minimum exceeds six. It never changes required-character or breached-password settings; an incompatible setting requires manual review. Signup must already be disabled.

The owner must confirm that the Supabase GitHub integration is connected to this repository and its `Supabase Preview` check is emitted by the Supabase GitHub App for each PR head revision. The Management API response must expose the branch's exact `git_branch`, `pr_number`, parent ref, nondefault flag, and health. Deployment proof comes from GitHub's check runs for the exact current PR head SHA: the latest matching `Supabase Preview` run must belong to the Supabase App, have a successful conclusion, and link to the selected child project at `https://supabase.com/dashboard/project/<child-ref>`. The check scan is limited to 100 runs; an incomplete or larger result fails closed. The child project must have a default `secret` and `publishable` API key. The deployed migrations must expose `app_members(user_id,role,active,can_manage_configuration)` through the Data API with the expected membership permissions. Missing prerequisites cause a bounded failure and can be reconciled by the next run or manual dispatch.

Both discovery and provisioning check out `main` by name, never PR code, and run only Node built-ins. The discovery job has no privileged environment or Supabase secrets. Its GitHub token has repository read, PR read, and checks read. It fetches the open PR and Supabase branch afresh, matches both exact branch name and PR number, verifies parent and nondefault child, and checks the Supabase App check's successful conclusion at the current PR SHA before changing Auth policy, user, or membership. It repeats these identity checks immediately before each mutation. Forked, closed, retargeted, stale, ambiguous, wrong-parent, and default targets are refused. No production project URL or key is constructed for the provisioning calls.

The script uses the verified child's temporary admin key only inside the workflow process to create or update the Auth user and `app_members` row, then signs in with the real password and reads the membership as that user. It does not call signup, invite, email, inventory, or production endpoints. Workflow logs contain PR number, abbreviated public commit SHA, and generic status only; HTTP error bodies are intentionally suppressed.

## Local validation

Run `npm run test:preview-access` and `node --check scripts/preview-access.mjs`. The preview test is included in `npm run validate:app`. The tests use fake API adapters and make no hosted writes. They cover idempotent reconciliation, password reset, sign-in/membership verification, and zero-write refusals for fork, stale revision, default/parent/wrong-parent branch, invalid check identity or child link, incomplete check listing, and absent schema. A real hosted branch/account verification remains necessary after the patched workflow reaches the trusted default branch; a PR workflow executes the existing default-branch script, not its proposed patch.

The flow is intentionally limited to GitHub-managed PR previews. It does not provision arbitrary manual Supabase branches.

## Preview file-key reconciliation

The same protected, trusted-main provisioning job can configure private inventory files after staff provisioning succeeds. Missing Vercel file configuration produces an explicit status and leaves the staff result intact. During one-time setup, the owner adds `PREVIEW_VERCEL_TOKEN` as an environment secret and pins environment variables `PREVIEW_VERCEL_PROJECT_ID` and `PREVIEW_VERCEL_TEAM_ID`. The configured project identity is `prj_t7N4Su8pUl2JH6NmAcBsa43MHekK` (`it-inventory-system`), under team `team_fBxB6q3lb8HvuuoYtcWPoaUz` (`phead2002`). Verify these identities and token access at setup; the automation rechecks the project/team and GitHub repository link on every guarded mutation. The Supabase Management token additionally requires database write access to verified child projects. After this setup and the owner's merge into trusted `main`, ordinary PR changes can reconcile each verified preview automatically. Direct module execution before merge does not activate the GitHub-triggered workflow.

Each verified disposable child receives one randomly generated 32-byte hexadecimal secret, persisted under key ID `pvf<child-ref>`. The migration and application RPC/grants remain unchanged. A staged row has `accepts_new=false` and `verify_until='-infinity'`; retries read the same persisted secret and never overwrite its ID. Only that exact secret and staged sentinel can transition to active with `verify_until='infinity'`. An inactive row with any other expiry is retired or foreign and cannot be reactivated. Intentional retirement sets `accepts_new=false` and a finite expiry sufficient for outstanding validation leases; never restore the staging sentinel. An existing foreign active key stops automation. A preview with an existing manual key or applicable manual environment value requires an explicit operator-controlled handoff before automation can own its configuration. The workflow does not retire manual keys or remove manual environment values.

Before each write, the workflow checks the open same-repository PR and frozen SHA, exact branch/PR Supabase child association, parent/nondefault identity, successful Supabase App check for that SHA, private key schema, pinned Vercel project/team/repository and nonproduction branch. It verifies both `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Every guard reads the verified child's authoritative Management API key listing; the exact configured public value must be classified as `publishable` or legacy `anon`, never secret/service-role. Opaque key contents are not decoded to infer identity. Missing, malformed, duplicate or contradictory broader preview values stop reconciliation. The canonical application currently has no separate server URL override. The automation accepts only its strictly marked, branch-specific sensitive `INVENTORY_FILE_KEYS_JSON` environment variable with secret visibility and exactly the preview target. Manual or broader applicable preview file-key values stop reconciliation; production-only values remain outside this operation. Updates target an observed exact environment ID after a fresh ownership/scope/revision check, without broad upsert.

The provider adapter omits `visibility` from the [Vercel v9 environment PATCH request](https://vercel.com/docs/rest-api/projects/edit-an-environment-variable), whose strict request schema rejects extra fields. It also omits `key`: [saved Sensitive/Secret names cannot be edited](https://vercel.com/docs/environment-variables/sensitive-environment-variables#edit-environment-variables), even when the supplied name is unchanged. PATCH still targets the observed exact environment ID and retains `type=sensitive`, the exact preview branch/scope, persisted value and intent comment. Both pre-write ownership and post-write readback require the expected key and `visibility=secret`; transport omissions do not relax the secret policy. Creation retains both fields.

The order is database stage, branch environment write, fresh GitHub-source deployment using repository ID plus branch ref and exact SHA, an eight-minute readiness deadline (individual HTTP requests are capped at fifteen seconds), fresh guards, and conditional activation. Deployment requests omit `target`, which means preview; they never use `deploymentId` redeployment, production/custom targets, or manual aliases. An automation-owned environment marker from a previous child or database generation can be replaced only after the current child association and persisted generation are verified. Unmarked/manual state is never adopted.

A nonsecret v2 intent records child, SHA, secret-generation fingerprint, backend configuration fingerprint and attempt number 1–3 in both the owned environment comment and deployment metadata. The backend fingerprint binds both canonical variable names, environment IDs, revisions, scopes and value digests. A recovered deployment must match that exact persisted intent, pinned project/repository/ref/SHA, and creation time after both intent and backend revisions. READY reuses the deployment; a known nonterminal state waits within the deadline. Only a freshly hydrated, fully validated ERROR/CANCELED deployment permits the next persisted attempt, after fresh source/backend/key/environment guards. The same database secret is written with the successor marker and read back before one new deployment POST. At most one POST occurs per invocation, and three attempts are allowed across reruns of that operation.

Missing, duplicate, inaccessible or unknown-state operations never advance. An intent with no matching deployment is explicitly uncertain: it can represent a crash before POST or a lost POST response. A lost POST response is recovered only from an unambiguous exact marker; a lost environment-write response stops without POST, and a committed marker without a deployment remains uncertain on rerun. A distinct SHA or generation can begin a fresh operation, subject to current guards; changing SHA alone never erases backend configuration drift detection for the same child/generation. An environment comment alone never establishes a secret value.

Strictly owned v1 state remains compatible. For the same child/generation, the legacy URL-only fingerprint must still match freshly verified URL configuration; the public key is independently bound by the new guard. For the same SHA, the original marker/revision and hydrated deployment must be recovered and validated. A nonterminal v1 deployment waits; a conclusive READY, ERROR or CANCELED v1 deployment migrates automatically to v2 attempt 2 and a fresh deployment with the same persisted secret, counting the legacy deployment as attempt 1. Legacy uncertainty or a URL fingerprint mismatch is never ignored. The URL-only fingerprint is retained solely for this migration.

These are provider configuration and request-provenance checks, not inspection of compiled bytes or hosted file acceptance. After activation, independent hosted verification must confirm the actual backend and exercise signed-in upload, server validation, publication and authenticated download. There is no recurring key cron. Preview infinity is limited to this disposable-child automation; production key installation and rotation remain owner-controlled.

The Management SQL uses single parameterized statements under READ COMMITTED, consuming the existing materialized file-guard lock. Staging uses `ON CONFLICT DO NOTHING` followed by a separate fresh read. Activation uses exact ID/secret/state compare-and-set; row rechecks refuse concurrent retirement and the unique active-key index rolls back a competing activation. A lock wait does not refresh a statement's snapshot. `tests/integration/preview-file-keys.mjs`, registered in the canonical database gate, checks these cases using independent connections. Offline adapter tests do not replace that database proof or hosted acceptance.
