# Field authoring and entry

The Add field dialog is a native viewport-centered modal with bounded scrolling and persistent Cancel/Add actions. Section headings and options are edited directly on the canvas; focusing a section heading selects the destination for the library's Add field action. Each section also has its own Add field action. There is no separate section inspector.

## Native browser zoom acceptance

The navigation-workflow browser regression checks scrolled opening, active arrival transforms, 390px and short viewports, keyboard focus trapping and return. Actual 200% browser zoom is an additional headed-browser acceptance case: open a selected category designer at 100%, record `window.devicePixelRatio`, use the browser's zoom control to select 200%, and verify the reported pixel ratio doubles while `document.documentElement.style.zoom` remains empty or `1`. Scroll to the section's Add field action and open it; record the dialog bounds against `window.innerWidth`/`innerHeight`, verify centered placement with at least 16px edges, and exercise internal scrolling, both actions, Tab/Shift+Tab, Escape and focus return. Repeat with a narrow browser window and a short height, recording the actual resulting CSS viewport. Restore browser zoom afterwards. Retain screenshots, interaction video and the metrics with the tested commit. CSS zoom, viewport resizing and CDP page/pinch scale do not establish this acceptance case; headless Playwright keyboard events may not execute browser-chrome zoom accelerators.

The registry has twelve supported custom types. Field authoring keeps definitions, visible placements and disposable preview answers separate. Add field opens a staged dialog with readable type names, purposes and examples; Add to form creates the definition and placement in one undoable local edit. Cancel or Escape restores focus without adding either. Use existing field and Standard fields share that picker, with Go to field, Show and Add to this section actions and visible incompatibility reasons.

The selected-field inspector groups Basics, Choices, Optional rules and Appearance. Defaults initialize only new records. Rules and initial-value editors use the same type input adapters as inventory forms. Optional limits start unconfigured; enabling a limit requires a valid value before Add or Save. Empty and incomplete enabled limits remain recoverable drafts with inline errors until corrected or unchecked. Published type and currency meaning stay immutable; Advanced offers explicit replacement and retirement, while unpublished local types can change without replacing their identity. Normal Move up/down moves a visible placement. Section changes preserve effective applicability; ancestor and legacy placement restrictions never expand silently.

Hide from form retains the field definition and stored answers. Required custom fields require an explicit confirmation to become optional before hiding. Sections containing required fields cannot be hidden or exclude their required form types; Name, Category and serialized Asset tag remain visible. Hidden fields includes hidden sections, individual fields and compatible unplaced legacy definitions. Retirement continues through Save changes and its existing impact confirmation, preserving immutable revisions, values and history.

Undo and whole-document restoration reset setting draft displays to the restored definition, while ordinary typing retains incomplete recoverable drafts. A broken placement is explicitly identified as Missing field and can be removed without inventing a definition or removing other fields or stored answers; the owner can then place an existing field through Add field. This repair is undoable.

The canvas uses inert, faithful field inputs with their configured descriptions. Try form uses the live inventory form renderer with disposable answers, including checkboxes and a searchable choice tree. The shared adapters use distinct DOM IDs for canvas, defaults, bounds and preview. Operational stock, identity, status and authorization remain outside custom metadata.

## UX reference and boundaries

Freshservice's [asset custom-field guide](https://support.freshservice.com/support/solutions/articles/50000012105-configure-custom-fields) informs the name/type/settings/Save flow, but its page applies to new signups after March 31, 2026. Its [dependent-field examples](https://support.freshservice.com/support/solutions/articles/156451-understanding-dependent-fields) and [Field Manager guide](https://support.freshservice.com/support/solutions/articles/154126-manage-ticket-fields-with-field-manager) describe ticket forms. They do not prove equivalent behavior in the owner's asset tenant. Their example three-level flow, API limitations, resource limits, deletion policies, branding and subscription features are not this application's contracts. No integration or tenant change is included.
