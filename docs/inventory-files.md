# Private inventory files

Serialized assets may have up to 20 ready photos/PDF documents. Quantity definitions have one ready recognition photo, independent of stock balances. A replacement keeps the old ready file visible until the new file commits. Active staff can add, replace, rename, and remove attachments on active, archived, or retired records. A separate attachment collection revision starts at `1` and advances only when a file is published, renamed, replaced, or removed. These actions do not change the inventory version, stock, or inventory event history. Append-only file events record actor, action, title before/after, file type/size, and resulting collection revision.

The `inventory-files` bucket is private. Browser uploads and downloads use the signed-in user's Supabase session. A browser first requests `/api/inventory-files/reserve` using its current authenticated session. The server checks parent authority and a usable active server key; `inventory_file_reserve_ready` verifies a short HMAC bound to the actor, parent, exact collection/replacement versions, UTF8-hex filename, type, size and active key before creating the same random, permanent source reservation. Missing or mismatched server/DB signing keys fail before reservation or Storage bytes. Reservation retains its existing identity semantics; it does not add receipt replay. Old unsigned `inventory_file_reserve` callers must reload the application and cannot create fresh reservations. This configuration check does not validate the selected content or guarantee later provider availability; Storage INSERT preflight checks the live, locked reservation, active staff membership, and expiry. Storage can finish streaming in a later privileged transaction, so a bucket-scoped completion trigger rechecks the locked lifecycle, uploader, generation, capability, key and wall-clock expiry at the actual object INSERT. Its UPDATE guard allows access timestamps but blocks changes to path, owner, version and content metadata, including a privileged conflict upsert after publication. No ordinary Storage UPDATE policy exists. Storage SELECT permits authenticated object reads and info for ready variants and the uploader's pending source; list is denied. A ready PDF reads its inspected original; a ready photo reads only normalized display/thumbnail JPEGs. Storage DELETE requires a current actor-bound cleanup claim and rechecks terminal, unreferenced state. Public metadata cards omit paths, object identities, validation receipts, and capabilities. Public direct table reads/writes are denied; metadata changes use RPCs.

The inventory list uses one member-only, 25-parent bounded projection for ready photo thumbnails and photo/PDF counts. It returns an exact ready thumbnail read path only after publication closes that object's INSERT window; pending, source-photo and removed paths never appear. The ordinary file cards still omit all paths and capabilities. Thumbnails are fetched through authenticated Storage when they enter the viewport; blob URLs are revoked on unmount. Quantity rows show the primary recognition photo, and asset rows show one representative photo plus file counts. The detail panel provides all ready files, full photo preview and PDF attachment download.

The upload states are reserved → uploaded → validating → validated → ready; rejected, cancelled, expired and removed are terminal. Storage upload and database reservation/publication are separate transactions; a failed step leaves a recoverable pending record or cleanup claim, never a ready file by assumption. Each object separately moves held → eligible → claimed → deleted. Object paths remain in permanent tombstones after deletion and are never reused. Validation records the exact Storage object UUID and version. A request-bound five-minute lease with 30-second grace serializes validation (one per actor, two per environment). An interrupted validation can be retried after grace; abandoned records expire. Validated files remain available for explicit renewed review for up to 24 hours. A stale collection or replacement file does not discard the uploaded bytes: the user reloads current file state and chooses Review and publish, which creates a new validation generation and reinspects the source. The original source stays private during this review.

Server validation downloads no more than 20 MiB using the caller's JWT. A resource-limited worker has a 20-second hard termination limit, 256 MiB old-space limit, and bounds images to 25 megapixels. It accepts decoded JPEG, PNG and still WebP, normalizes orientation, strips EXIF by re-encoding, and creates 1600-pixel display and 320-pixel thumbnail JPEGs. HEIC/HEIF requires conversion by the user. PDFs must parse structurally with `pdf-lib`, be unencrypted, contain 1–250 pages and at most 10,000 indirect objects. PDFs download as attachments and are never embedded for preview. This is structural inspection, **not malware scanning**. The original PDF remains live; an original photo becomes cleanup-eligible only after its derived variants commit.

The inspection worker identifies invalid or unsupported decoded content with a typed error. Only that terminal content failure rejects the pending file; the rejection then invokes bounded, actor-authorized cleanup. Storage/download failures, stale review versions and other infrastructure errors leave the staged file available for an explicit retry. No client-provided validation flag or decoder-message text can turn a transient failure into a rejection.

Server-only HMAC keys are installed separately per environment in `private.file_keys` and `INVENTORY_FILE_KEYS_JSON` (a JSON map from key ID to at least 32-character secret). The migration contains no keys. A derived upload path carries an opaque HMAC bound to actor, file, generation, variant, nonce and expiry. A separate HMAC is required to register the exact Storage object. Versioned `v2` final validation signs parent kind/ID, reviewed collection revision, request ID, key, lease expiry, purpose, replacement ID and reviewed file version, source object identity/version/type/bytes/digest, and both derived object identities/versions/bytes/digests. Finalization verifies the current key, lease, request, generations, collection/replacement revisions and object metadata in one transaction with an append-only file event and receipt. Completed receipt replay first reauthorizes active staff and is independent of current key/lease expiry. The frontend never sees keys or derived capabilities before readiness.

The validation-begin and cleanup-claim/confirm RPCs additionally require a short server HMAC proof; calling them directly from a browser does not reveal source object generations or terminal unpublished paths. The active key ID is public to staff, but its secret never leaves the server/private database.

To rotate, install a second key in the private DB and both server keys in `INVENTORY_FILE_KEYS_JSON`; then switch `accepts_new` to the new DB key in one transaction. Keep the old key verifiable through the longest active validation lease plus grace, then retire it. Completed receipt replay does not require the retired key. Keep each environment's keys distinct. Missing keys disable only the file workflow, with a configuration message; existing inventory remains available. See [deployment](deployment.md#private-inventory-file-configuration) for isolated-preview proof and the separate production prerequisite.

Reservations account atomically under a guard row for three active pending files per actor, 20 ready asset files, one ready quantity recognition photo, 128 MiB staging and 768 MiB ready storage. Image reservations charge a 60 MiB worst-case allowance for each quota until source cleanup is confirmed; PDFs charge 20 MiB. Every source object carries a full 20 MiB charge until its actual size is reconciled against Storage under lock or its physical absence is confirmed. The browser's declared size never reduces terminal quota accounting, including cancellation before the uploaded RPC. Replacement charges both old and new until cleanup confirms deletion. Ready bytes include removed objects until confirmed deletion. Cleanup selects a bounded batch of terminal, unreferenced objects; a caller with a short claim lease asks the Storage API to delete each and confirms metadata absence through an RPC. A failed or interrupted deletion remains claimable after expiry. The staff cleanup route is also called after normal publish/remove actions; it can be retried by a staff session. Every call supplies the exact parent kind/ID. Parent filtering applies to expiry, eligibility, claiming and returned prior claims; it cannot maintain files on other records. Legacy global cleanup claims require an application upgrade.

Cleanup first obtains an authoritative parent-scoped status after active-staff and parent authorization. It counts all undeleted objects other than currently referenced ready objects, including held pending bytes, tombstones awaiting deletion, validation grace and other actors' in-flight claims. Zero work returns `no_work` without key lookup, claims or Storage DELETE; unavailable or forbidden discovery is an error, never zero. After an attempted batch, a second authoritative read can report `complete` only when no work remains. Responses include `deleted`, `failed`, `outstanding`, `blocked`, `pending` and `status`; status is `partial` when some confirmations fail after deletions, `failed` when all confirmations fail, or `pending` for remaining work without a confirmation failure. A claim batch alone cannot certify that all cleanup is complete. A newly rejected or cancelled source can remain unclaimable until its validation lease plus 30-second grace expires, even while unrelated older claims are deleted. The panel therefore keeps an explicit retry control while authoritative work remains or discovery fails; a cleanup failure never reverses a committed publish, cancellation or removal. Object byte charges are released only when Storage absence is confirmed by the database. Active pending slots follow the existing expiry windows (reservation plus 30 seconds, uploaded reservation plus one hour, validating lease plus 30 seconds, and validated creation plus 24 hours); a live validation lease and its grace always retain capacity. Expired work on another parent is never rewritten or cleaned by a reservation. Its undeleted source and derivative objects remain charged, including held objects without a reconciled Storage identity. A caller may explicitly renew abandoned validation, but renewal atomically re-enters both actor and staging quotas under the same guard; failed admission rolls back the generation and lease. Full worst-case validation allowance remains charged through a worker lease and grace, including terminal work; expiry alone never proves physical absence.

`npm run validate:db` resets and tests the local Supabase stack, including real Storage HTTP upload/download policy and physical-byte checks. The focused completion test observes Storage blocked after preflight and checks ready PDF bytes against a queued duplicate, cancellation/cleanup against a late write, derived generation rejection, natural key expiry during a key-lock wait, and a forbidden unregistered path with no object. `tests/integration/files.ts` uses an ephemeral **local-only** signing key. `npm run test:e2e` generates a separate per-run local key, passes it only to the child build/browser process, then expires the key and shreds its secret in a `finally` block. Published test-file foreign keys leave an inert key-ID tombstone, not a live signing capability. For manual local browser use, put `INVENTORY_FILE_KEYS_JSON` in untracked `.env.local` and install the same ID/secret into the local private key table; never commit the secret. Local Storage is enabled in `supabase/config.toml`. Provision only an explicitly authorized, verified isolated nonproduction preview; its proof must exercise actual authenticated Storage and server validation. Production key installation, bucket/migration delivery and operation require the owner's production release process.

## Disposable-preview key lifecycle

After one-time protected environment setup and the owner's trusted-main merge, [preview reconciliation](preview-staff-access.md#preview-file-key-reconciliation) can manage one `pvf<child-ref>` generation per verified disposable Supabase child. It stages an inactive `-infinity` row, persists the secret once, configures a branch-only sensitive Vercel preview value, waits for a fresh exact-SHA deployment, then conditionally activates that same secret with `infinity` verification expiry. An inactive finite-expiry row is intentionally retired and never returned to staging. Existing manual active keys or applicable manual preview environment values require an owner-controlled handoff; production values and production rotation remain separate.

Failures leave staged keys inactive and preserve existing active keys. Reconciliation binds both the canonical Supabase URL and its public key to the verified child using authoritative key classification, environment IDs/revisions/scopes and value digests. Persisted v2 intents allow up to three deployment attempts per operation, with one new POST per invocation and fresh proof of ERROR/CANCELED before a retry; READY is reused and nonterminal state waits. Strictly validated v1 state migrates to v2 attempt 2 with the same database secret. A response lost after a deployment request is recovered only from a bounded, unambiguous matching provider operation; missing deployments or unresolved same-intent ambiguity stop further POSTs. These configuration and deployment checks do not replace compiled-byte or signed-in runtime proof. Hosted file acceptance remains required after setup and activation. No key is committed, logged, or exposed through a new application RPC.

## Detail-panel presentation

Recognition photo and Photos and documents lead with ready content and staff Add photo/Add attachment controls. Ready quantity photos offer replacement; the prior usable photo remains until publication succeeds. Pending cards explain upload confirmation, explicit Review and publish, validation in progress, or awaiting publication without claiming readiness or invented progress. Files supplied by the authorized projection remain visible to a viewer, but mutation controls require staff. The projection exposes only ready files and the caller's own recoverable pending files; terminal files are represented by action feedback and file activity, not an invented persisted card feed.

File sizes use the shared binary B/KiB/MiB formatter. Zero bytes and unavailable metadata are distinct. A collapsed File activity area retains authorized history paging and staff cleanup. Cleanup results and actual errors remain visible beside the main file work. Authoritative no-work and completion clear the retry state; pending work and partial/failed cleanup retain it. A failed activity read is not presented as empty history.

Panel state is bound to the authenticated actor, parent kind/ID and staff capability. Switching these identities remounts the panel, clears its picker, replacement, preview and messages, and ignores late private read results. Confirmed removal/replacement invalidates the prior file tile and preview even when collection refresh fails. Private reads still use the existing authorized RPC and authenticated Storage download; no public file URL is used.

Component state fixtures cover pending and terminal presentation, role restrictions, actor/record switches and cleanup failures. These are UI-state evidence, not hosted publication or physical-byte deletion proof. Hosted validation/cleanup prerequisites must still be exercised through the existing runtime; unavailable publication and unconfirmed cleanup remain explicit, and E01/E02 remain open until independently verified.
