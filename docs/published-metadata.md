# Published inventory metadata

The designer's category selector contains lightweight references to all eligible categories and opens the selected category's own URL; only that category's form is loaded. The URL, heading, draft baseline, save target and recovery identity stay together. The Try form Category input remains an inventory preview input. Category switches ask before discarding unsaved edits or an unadded field, and a failed load keeps current input available for retry. A save in progress blocks supported link/selector navigation. Browser Back/Forward preserves unsaved definitions, pending field input (including unresolved date/time and display timezone), and uncertain-save receipts in the existing bounded session recovery, scoped to actor, backend and category; returning offers explicit recovery or discard. Browser history traversal cannot be universally blocked through the App Router. If browser storage is unavailable, the editor warns that history traversal cannot guarantee recovery; supported links and unload still prompt. No history interception or background form preloading is used. An unknown designer-save outcome freezes editing, discard and supported navigation until Retry original save checks the same immutable payload and request ID; recovery retains the confirmed review token rather than issuing a replacement operation. Definitive domain rejections unlock editing.

Inventory metadata editors reconcile the original baseline, actual dirty intent and current authorized record. Latest untouched or converged fields are retained; overlapping fields offer readable latest/mine choices tied to the exact record, category and schema snapshot. Category and custom answers form a dependency group. Validation and lifecycle changes require targeted review; compatible layout and presentation changes can be adopted. Existing v2 compare-and-swap RPC enforcement remains. At most one automatic revised attempt after a definitive stale rejection gets a new request ID. An uncertain outcome freezes editing and Cancel and replays the exact payload and request ID before reconciliation. A confirmed commit followed by a fresh authorized read resets the complete baseline and values; failed refresh offers a saved-record refresh retry and is not reported as an unknown commit.

An uncertain designer receipt also locks the recovery banner's discard action and supported navigation before Recover edits is selected. A cancelled category choice leaves an earlier load valid. After an accepted switch passes its access and form preflight, the outgoing editor stays frozen until the target designer actually mounts. A 15-second route-commit deadline removes the reviewed source draft's discard marker before allowing new edits; a late target mount then retains those fresh source edits for explicit recovery. If storage prevents safely removing that marker, the editor stays paused and explains the limitation. Browser Back/Forward still uses scoped durable recovery rather than history interception.

## Current read and publication refinements

Publication refreshes `needs_metadata` for current-category records in the same pointer-change transaction after deterministic row locks and review recheck. It computes each derived flag once and updates changed flags as a set. A database timeout rolls back the pointer and all flags together without changing item versions, timestamps, values, provenance or business events.

Inventory detail retains complete custom values and provenance. Search displays a visibly abbreviated custom summary (about 900 characters per record) and reads at most 25 persisted record identities per page; open a record for the complete values. History list/detail projects core before/after snapshots without raw `custom_values`, marks events containing or changing custom data, and offers a separate bounded field-by-field snapshot view. That view pages at most 16 option paths at a time and caps its UTF-8 result at 2 MiB. Active membership and event authorization are checked inside the read RPC. Invalid identities, offsets and unavailable events fail explicitly.

Each category points to one current published form revision. Untouched categories point to a shared immutable baseline containing the canonical core controls. Save changes creates the next category-owned immutable revision and changes the category pointer atomically after validation and any required impact confirmation. Legacy draft revisions remain recoverable with their original identity and version. Published field UUIDs belong to one category and one type forever; option UUIDs belong to one field forever. Changing a field type or the meaning of a currency field requires a new field UUID. Old revisions and option labels remain available for history, retired fields, retired choices and legacy values. An untouched category with no inventory references can still be deleted; authored revisions or source-field values make a removed category a retained tombstone.

Only an active staff member with `can_manage_configuration` may save the active form or use the compatibility draft/review/publish RPCs. The remaining draft identity and locking details in this paragraph describe those compatibility RPCs. Active members may read published forms. A draft is a JSON document and may contain invalid semantic content; publication compiles it into relational field, option, section and control rows only after full validation. Every draft save, discard, publication review and publish call carries the original draft UUID, decimal-string draft version, current published revision UUID and expected actor UUID. The no-draft baseline is an explicit null draft UUID with version `0`; an existing draft requires its own UUID and positive version. The server independently checks `auth.uid()` and active maintainer membership, then rejects a different expected actor. Review uses the supplied baseline and never silently reviews a newer draft. Publish also requires a fresh impact review token bound to that draft identity, version, published pointer, actor and referenced inventory. A discarded draft followed by a different draft at the same version is stale, as is a changed published pointer. Authorized completed receipt replay occurs before live baseline checks, so retrying the exact completed request returns its original result. Publish and category lifecycle changes take the exclusive catalog lock; draft save/discard and reference-changing inventory writes take the shared lock. First-draft saves also lock their category row before looking for a draft, so concurrent null/version-`0` saves produce a stale-draft result instead of a unique-constraint error. Publication locks current quantity records by UUID and then serialized assets by UUID before rechecking the reviewed reference fingerprint; a concurrent stock mutation makes the review stale. Publication updates `needs_metadata` for every current-category record, including archived and retired records, in the pointer-change transaction. This derived flag refresh does not change item versions, timestamps, values, validation provenance or inventory events. Both use fresh read committed transactions. Database functions advertise a five-second execution budget and a two-second catalog lock wait.

The definition document has exactly `fields` and `layout` arrays. A field has stable `id`, `type`, `label`, `applies_to` (`quantity`, `asset`, or both), `required`, optional `help`, `rules`, `default`, and optional `options`. Option entries have stable `id`, `label`, `active`, and optional `parent_id`. A layout is ordered sections, each with an ID, label and ordered controls. Controls have an ID, `kind` (`field`, `builtin`, or `help`) and width `Auto`, 3, 4, 6, 8, 9 or 12. Field controls reference a field ID; builtin controls reference a supported operational column. Name and category must each occur once. Required custom fields must have reachable controls. Stock, status, record identity and security remain operational columns outside the builder. Settings provides the visual designer described below; the definition remains a versioned JSON document at the persistence boundary.

The supported data types are short and long text, safe integer, canonical decimal string (at most 24 digits and six fractional places), boolean, date (`YYYY-MM-DD`), offset datetime normalized to UTC, credential-free HTTP(S) URL, currency (`{amount,currency}` with fixed ISO code and precision at most four), single selection, multiple selection and hierarchical selection. Currency codes are checked against a pinned copy of [SIX ISO 4217 List One](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml), published 2026-09-17; code-list changes require a reviewed migration and never change an existing field's meaning. Any active hierarchy node is selectable. The compiler limits 100 active fields, 1,000 options per field, 5,000 per revision, and 64 ancestor levels. It rejects unsupported rule keys, invalid or inverted bounds, invalid defaults, duplicate controls, option cycles and unreachable parents. Defaults appear on a new form and become persisted only when the new record is saved. Missing, false, zero and empty string are distinct; JSON null is rejected for a set value, and `unset` is explicit.

`quantity_create_v2`, `quantity_update_v2`, `asset_create_v2` and `asset_update_v2` carry the current published revision UUID. Updates also carry the item version. `custom_patch` has disjoint `set` (field UUID to value) and `unset` (field UUID array); omitted fields stay unchanged. The database stores `custom_values` as a JSONB object keyed by canonical field UUID, with `{value,validated_revision_id}` generated by the server. The complete stored object is limited to 256 KiB UTF-8. Core and custom edits produce one version, event and receipt. Identically resubmitted historical values keep their original provenance. New or changed values must satisfy current rules. A record can retain an unchanged value that a later revision tightens; `needs_metadata` flags a current-rule gap. New records and ordinary category changes must satisfy current required fields. Source custom values remain inspectable after an explicit category change and are never mapped by matching labels. When a v2 update changes category and existing custom values become legacy, the user must explicitly check the acknowledgement in the review UI; the server requires boolean `acknowledge_legacy_values: true`, bound to the item version, target published revision and receipt. Old callers may update core metadata in the same category without erasing custom values; old category changes with custom values fail with a client-upgrade error even when the target has no required fields.

Inventory detail, history and search present custom labels, values, validation revision and option paths from the immutable revision where the value was validated. Historical category labels come from event snapshots when available; a current name is never presented as a historical name. Retired or source-category values remain visible as legacy values. The responsive renderer shares this definition and `controlLayoutStyle` contract with the visual designer. Controls stay in document order and flex-wrap at their preferred twelve-column span, with the inter-control gap included in that width. `Auto` has a compact preferred span and grows into available width. Each control has a minimum usable width that clamps to the viewport; compact boolean controls can share a phone row when space allows. Compatible schema presentation changes are adopted without erasing input. Consequential schema or category changes retain input and require targeted review; descriptive record changes use the safe reconciliation and field-specific conflict choices described above. Ordinary editing has no manual record-version adoption control.

Category removal impact review includes current and historical inventory counts, authored revision count, records retaining source-field values, and projected quantity/asset records that will need metadata under the target form. The reviewed removal transaction retains source custom values and their validation revision, changes the record's last checked revision to the target published form, and computes `needs_metadata` without inventing replacement values. A target is mandatory when current or historical inventory references exist. Authored history alone can be tombstoned without a target. The review token binds these counts and is rejected if the referenced records or category versions change. The removal event snapshots both core and custom metadata before and after reassignment.

The inventory export RPC preserves existing columns and adds `Custom Fields JSON` only when `customFields=true`. The JSON column is keyed by field UUID and carries value, field-owner category, validation/current owner revision, label and option path. A retained source-category value continues to identify its source category after reassignment; the export row identifies the record's current category separately. One stable database statement supplies a consistent snapshot. The database caps compact matching inventory identity keys or low-stock item keys at 10,001 before row hydration and sorting. Low-stock filters for query and location match the same holding row. The database checks nested holdings and custom output as it builds them, and rejects over 10,000 rows or 2 MiB complete JSON. The server reads the raw PostgREST body with a 2 MiB cap before JSON parsing, builds a complete CSV in memory with UTF-8 byte accounting, and rejects a file over 3 MiB before sending success headers. The route has a ten-second deadline; timeouts are retryable and never produce a partial file. The UI offers the plain export and an explicit custom-field export. A 413 response asks for narrower filters, fewer records or custom fields disabled; a single oversized record can be retried without custom fields. There is no background export job. Preview-only export diagnostics require an explicit server opt-in and record only anonymous byte, timing and sampled-memory measurements; they do not constitute a continuous peak-memory proof.

Settings provides a visual form designer for configuration maintainers. Add field stages a named type, description, scope, choices and optional rules before adding its definition and placement as one undoable edit. Cancel/Escape creates neither. One selected inspector presents Basics, Choices, Optional rules and Appearance; advanced identity, replacement and retirement stay in Advanced. The same picker offers existing and standard fields, with placement destinations, Show, Go to field and incompatibility explanations. Instructions are distinct section blocks. The editor keeps placements in document order, with held drag reflow, keyboard Move up/down, section relocation and snapped widths. A bounded local undo history and guards for category changes, link clicks and page reloads protect unsaved edits. Dirty edits are also held in the current tab's session storage under the authenticated member, environment and category. On re-entry the maintainer explicitly recovers or discards those edits; recovery retains the original draft and published revision baselines, and a changed server version is called out before saving. Save, discard and signout clear only the designer's recovery keys. Unavailable browser storage is shown as a limitation. This recovery path covers client-side browser Back/Forward without changing browser history. An unpublished local field can change type while retaining its UUID; changing a published field type requires an explicit replacement with a new UUID; currency code and precision of a published field are locked. Hide from form retains field definitions and values for recovery. Required fields must become optional through explicit confirmation before hiding; protected standard fields remain visible. Advanced retirement removes a field from the new revision without erasing historical values. The inert canvas and interactive desktop/phone Try form use the shared field renderer used by inventory, with a separate notice for operational stock, location, status, identity and permission controls.

The editor exposes one Save changes action. It validates the current local document and sends its exact actor, published pointer and legacy draft identity/version baselines to `metadata_form_save`. An ordinary change publishes atomically; a consequential change returns a review token and impact counts, then Confirm and save changes submits the same reviewed payload. There is no separate user-managed save-draft/publish ceremony. Legacy draft RPCs remain supported for compatibility and recovery; they do not define the everyday editor workflow. A conflict leaves entered edits and the original version baseline intact until the maintainer explicitly refreshes. The local issue list is a guide; the database compiler remains authoritative for currency codes, defaults, resource limits, field and option identity, hierarchy validity and layout. File attachments are separate and do not alter the metadata field types or custom value envelope. Local database, browser and hosted PostgREST acceptance remain separate validation gates; a static or mocked pass does not certify the SQL lock, byte, or authorization boundaries.
