# Published inventory metadata

Each category points to one current published form revision. Untouched categories point to a shared immutable baseline containing the canonical core controls. The first saved draft creates a category-owned revision; publication keeps that revision immutable and changes the category pointer atomically. A later draft receives the next revision number. Field UUIDs belong to one category and one type forever; option UUIDs belong to one field forever. Changing a field type or the meaning of a currency field requires a new field UUID. Old revisions and option labels remain available for history, retired fields, retired choices and legacy values. An untouched category with no inventory references can still be deleted; authored revisions or source-field values make a removed category a retained tombstone.

Only an active staff member with `can_manage_configuration` may save or discard a draft, review publication impact, or publish. Active members may read published forms. A draft is a JSON document and may contain invalid semantic content; publication compiles it into relational field, option, section and control rows only after full validation. Every draft save, discard, publication review and publish call carries the original draft UUID, decimal-string draft version, current published revision UUID and expected actor UUID. The no-draft baseline is an explicit null draft UUID with version `0`; an existing draft requires its own UUID and positive version. The server independently checks `auth.uid()` and active maintainer membership, then rejects a different expected actor. Review uses the supplied baseline and never silently reviews a newer draft. Publish also requires a fresh impact review token bound to that draft identity, version, published pointer, actor and referenced inventory. A discarded draft followed by a different draft at the same version is stale, as is a changed published pointer. Authorized completed receipt replay occurs before live baseline checks, so retrying the exact completed request returns its original result. Publish and category lifecycle changes take the exclusive catalog lock; draft save/discard and reference-changing inventory writes take the shared lock. Both use fresh read committed transactions. Database functions advertise a five-second execution budget and a two-second catalog lock wait.

The definition document has exactly `fields` and `layout` arrays. A field has stable `id`, `type`, `label`, `applies_to` (`quantity`, `asset`, or both), `required`, optional `help`, `rules`, `default`, and optional `options`. Option entries have stable `id`, `label`, `active`, and optional `parent_id`. A layout is ordered sections, each with an ID, label and ordered controls. Controls have an ID, `kind` (`field`, `builtin`, or `help`) and width `Auto`, 3, 4, 6, 8, 9 or 12. Field controls reference a field ID; builtin controls reference a supported operational column. Name and category must each occur once. Required custom fields must have reachable controls. Stock, status, record identity and security remain operational columns outside the builder. The current editor in Settings accepts JSON; the visual drag designer is the next slice.

The supported data types are short and long text, safe integer, canonical decimal string (at most 24 digits and six fractional places), boolean, date (`YYYY-MM-DD`), offset datetime normalized to UTC, credential-free HTTP(S) URL, currency (`{amount,currency}` with fixed ISO code and precision at most four), single selection, multiple selection and hierarchical selection. Currency codes are checked against a pinned copy of [SIX ISO 4217 List One](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml), published 2026-09-17; code-list changes require a reviewed migration and never change an existing field's meaning. Any active hierarchy node is selectable. The compiler limits 100 active fields, 1,000 options per field, 5,000 per revision, and 64 ancestor levels. It rejects unsupported rule keys, invalid or inverted bounds, invalid defaults, duplicate controls, option cycles and unreachable parents. Defaults appear on a new form and become persisted only when the new record is saved. Missing, false, zero and empty string are distinct; JSON null is rejected for a set value, and `unset` is explicit.

`quantity_create_v2`, `quantity_update_v2`, `asset_create_v2` and `asset_update_v2` carry the current published revision UUID. Updates also carry the item version. `custom_patch` has disjoint `set` (field UUID to value) and `unset` (field UUID array); omitted fields stay unchanged. The database stores `custom_values` as a JSONB object keyed by canonical field UUID, with `{value,validated_revision_id}` generated by the server. The complete stored object is limited to 256 KiB UTF-8. Core and custom edits produce one version, event and receipt. Identically resubmitted historical values keep their original provenance. New or changed values must satisfy current rules. A record can retain an unchanged value that a later revision tightens; `needs_metadata` flags a current-rule gap. New records and ordinary category changes must satisfy current required fields. Source custom values remain inspectable after an explicit category change and are never mapped by matching labels. When a v2 update changes category and existing custom values become legacy, the user must explicitly check the acknowledgement in the review UI; the server requires boolean `acknowledge_legacy_values: true`, bound to the item version, target published revision and receipt. Old callers may update core metadata in the same category without erasing custom values; old category changes with custom values fail with a client-upgrade error even when the target has no required fields.

Inventory detail, history and search present custom labels, values, validation revision and option paths from the immutable revision where the value was validated. Historical category labels come from event snapshots when available; a current name is never presented as a historical name. Retired or source-category values remain visible as legacy values. The responsive renderer shares this definition and `controlLayoutStyle` contract with the planned designer. Controls stay in document order and flex-wrap at their preferred twelve-column span, with the inter-control gap included in that width. `Auto` has a compact preferred span and grows into available width. Each control has a minimum usable width that clamps to the viewport; compact boolean controls can share a phone row when space allows. A changed published schema keeps entered values and asks for an explicit review of the new revision. A changed item version keeps entered values with the original version baseline until the user explicitly accepts the latest record version.

Category removal impact review includes current and historical inventory counts, authored revision count, records retaining source-field values, and projected quantity/asset records that will need metadata under the target form. The reviewed removal transaction retains source custom values and their validation revision, changes the record's last checked revision to the target published form, and computes `needs_metadata` without inventing replacement values. A target is mandatory when current or historical inventory references exist. Authored history alone can be tombstoned without a target. The review token binds these counts and is rejected if the referenced records or category versions change. The removal event snapshots both core and custom metadata before and after reassignment.

The inventory export RPC preserves existing columns and adds `Custom Fields JSON` only when `customFields=true`. The JSON column is keyed by field UUID and carries value, category, validation/current revision, label and option path. One database statement supplies a consistent snapshot. The database inspects at most 10,001 matched rows, checks nested holdings and custom output as it builds them, and rejects over 10,000 rows or 2 MiB complete JSON. The server reads the raw PostgREST body with a 2 MiB cap before JSON parsing, builds a complete CSV in memory with UTF-8 byte accounting, and rejects a file over 3 MiB before sending success headers. The route has a ten-second deadline; timeouts are retryable and never produce a partial file. The UI offers the plain export and an explicit custom-field export. A 413 response asks for narrower filters, fewer records or custom fields disabled; a single oversized record can be retried without custom fields. There is no background export job.

Settings now provides a visual form designer for configuration maintainers. Field and option UUIDs are created once. The editor offers labels, help, applicability, required flags, supported rules and defaults, hierarchy paths and parent navigation, ordered sections, help controls, and snapped widths. It keeps controls in document order and provides drag handles plus keyboard-accessible move, section and width controls. A bounded local undo history and guards for category changes, link clicks and page reloads protect unsaved edits. Dirty edits are also held in the current tab's session storage under the authenticated member, environment and category. On re-entry the maintainer explicitly recovers or discards those edits; recovery retains the original draft and published revision baselines, and a changed server version is called out before saving. Save, discard and signout clear only the designer's recovery keys. Unavailable browser storage is shown as a limitation. This recovery path covers client-side browser Back/Forward without changing browser history. Changing a field type creates a replacement with a new UUID; currency code and precision of a published field are locked. Removing a field from a new revision does not erase its historical values. The desktop and phone preview embeds the same live form renderer used by inventory, with a separate notice for operational stock, location, status, identity and permission controls.

The editor saves the current document as a draft even when semantic errors are shown. Publication requires the draft to be saved, a successful impact review, and the server's matching draft version, published revision and review token. A conflict leaves entered edits and the original version baseline intact until the maintainer explicitly refreshes. The local issue list is a guide; the database compiler remains authoritative for currency codes, defaults, resource limits, field and option identity, hierarchy validity and layout. File attachments are separate and do not alter the metadata field types or custom value envelope. Local database, browser and hosted PostgREST acceptance remain separate validation gates; a static or mocked pass does not certify the SQL lock, byte, or authorization boundaries.
